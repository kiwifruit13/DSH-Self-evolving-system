以下是深度研究后蒸馏出的三份技术文档，分别对应 **Skill-Creator**、**Skill-Judge** 和 **Agent-Builder** 三个元技能。

---

# 文档一：Skill-Creator 技术白皮书

## 1. 概述

**Skill-Creator** 是 Anthropic 官方维护的一个元技能（Meta-skill），其核心使命是将软件开发中的**测试、基准测试、迭代改进**等严谨流程，融入到 Skill 的创作过程中，让非技术背景的领域专家也能开发出高质量、可复用、可迭代的 AI 技能。它不是简单的模板工具，而是一套完整的 **AI 技能工程化系统**。

**核心定位**：教 AI 如何创建有效的 Skill——即“教 AI 教 AI”的元技能。

**核心目标**：解决三类关键问题——Skill 是否真能提升结果质量、是否能在正确场景下被精准触发、在模型升级后是否还能保持价值。

---

## 2. 核心设计理念

### 2.1 两类 Skill 的区分

| 类型 | 定义 | 评估逻辑 |
|------|------|----------|
| **能力提升型** | 让模型完成基础模型无法稳定做到的事情（如使用特定技术创建规范文档） | 重点看使用 Skill 与不使用 Skill 的结果差异 |
| **偏好编码型** | 按组织的工作流编排模型已有能力（如 NDA 审查流程） | 重点看是否能稳定遵守团队既定规范 |

### 2.2 核心原则

**原则一：上下文窗口是公共资源**
Skill 与系统提示、对话历史、其他 Skill 元数据、用户请求共享上下文窗口。每个词都要有价值，默认假设模型已经很智能，只添加它不知道的信息。

**原则二：设置适当的自由度**
指令的详细程度应与任务的易错程度相匹配——创造性任务给原则性指导，高风险任务给精确步骤。

---

## 3. 架构设计

### 3.1 文件结构

```
skill-creator/
├── SKILL.md          ← 32KB 的超详细编排指南
├── agents/           ← 子 Agent 指令
│   ├── grader.md     ← 评分 Agent
│   ├── comparator.md ← A/B 对比 Agent
│   └── analyzer.md   ← 分析 Agent
├── scripts/          ← 自动化脚本
│   ├── aggregate_benchmark.py
│   ├── run_loop.py
│   ├── run_eval.py
│   └── package_skill.py
├── eval-viewer/      ← 评估结果查看器
└── references/       ← 参考文档
```

### 3.2 三层信息模型（Token 经济学）

| 层级 | 触发条件 | 典型 Token 消耗 |
|------|----------|-----------------|
| **L0: 概览** | 始终注入 | ~30 Token/技能 |
| **L1: SKILL.md body** | skill_load 后 | ~500-2000 Token |
| **L2: 详细文档** | skill_select_docs 后 | ~1000-5000 Token |

如果有 20 个技能，L0 的总成本仅约 600 Token——这是“观望”的代价。一旦确定需要特定技能，L1 注入约 2000 Token 给出方向，最后按需加载 L2。

### 3.3 CQRS 模式应用

`_skill_processor.py` 的 `_inject_overview` 方法始终执行（L0），而 `_build_docs_text` 仅在 `_get_docs_selection` 返回非空列表时才执行（L2）。写入方 `skill_select_docs` 和读取方 `_build_docs_text` 之间通过 `state_delta["temp:skill:docs:pptx"]` 临时状态解耦——这是典型的 **CQRS（命令查询职责分离）** 模式。

---

## 4. 核心工作流

SKILL.md 定义了一条完整的 **CI/CD 式流水线**：

```
Capture Intent → Interview → Write SKILL.md → Run Tests → Evaluate → Improve → Repeat → Package
```

执行时 LLM 会：
1. 与用户对话确定技能范围（纯对话，无工具）
2. 写出新 Skill 的 SKILL.md（用 write_to_file）
3. 并行 spawn 子 Agent 做 A/B 测试（with-skill vs baseline）
4. 执行评估脚本，聚合测试数据，生成可视化报告
5. 收集用户反馈 → 修改 → 回到第 3 步循环迭代
6. 打包输出最终的 .skill 文件

### 4.1 多阶段执行方式

| 阶段 | 执行方式 |
|------|----------|
| 阶段 1-2 | 纯 Prompt（对话 + 写文件） |
| 阶段 3 | skill_select_docs 加载子 Agent 指令（渐进加载） |
| 阶段 4-5 | skill_run 执行评估脚本（脚本执行） |

---

## 5. 三大子 Agent 评估架构

Skill-Creator 内部使用三个专用子 Agent 互相校验，而非单一模型自说自话：

| Agent | 职责 |
|-------|------|
| **Grader** | 评分 Agent——评估单个 Skill 的执行质量，同时批判评估体系本身 |
| **Comparator** | 对比 Agent——对两个版本的输出做**盲评**，不知道哪个是哪个 |
| **Analyzer** | 分析 Agent——盲评结束后“揭盲”，分析胜者为胜的原因，给出具体改进建议 |

**关键设计**：Grader 的 Prompt 中明确要求：“You have two jobs: grade the outputs, and critique the evals themselves. A passing grade on a weak assertion is worse than useless — it creates false confidence.”

---

## 6. 关键技术细节

### 6.1 package_skill.py：分层排除设计

`should_exclude` 对目录和文件做了分层处理——`EXCLUDE_DIRS` 是全局排除的，`ROOT_EXCLUDE_DIRS` 只在 Skill 根目录排除（如 `evals/`）。这种设计避免了“用户 Skill 的子目录里恰好也有一个叫 evals 的文件夹”被误排除。

### 6.2 aggregate_benchmark.py：小样本统计严谨性

计算标准差时使用**样本标准差**（除以 n-1），而非总体标准差。对于小样本评估（默认每配置 3 轮 run），这是统计学上的正确选择——总体标准差会系统性低估真实波动。

### 6.3 防过拟合设计

改进模型完全看不到测试集，采用的是标准 ML 里 train/test split 的思路，确保技能的泛化能力。

### 6.4 实时报告

循环开始时会自动生成一个带 `<meta http-equiv='refresh' content='5'>` 的 HTML 页面并调用 `webbrowser.open()` 打开，用户可以在浏览器中实时观察当前迭代进度和分数变化。

---

## 7. 设计精髓总结

| 维度 | 体现 |
|------|------|
| **工程化** | 将软件开发的最佳实践（测试、基准测试、迭代）引入 Skill 开发 |
| **科学性** | 盲测对比、样本标准差、防过拟合——数据驱动的决策 |
| **Token 效率** | 三层信息模型 + CQRS，实现渐进式披露 |
| **元认知** | Grader 不仅评分，还批判评估体系本身 |


# 文档二：Skill-Judge 技术白皮书

## 1. 概述

**Skill-Judge** 是一个专门用于评估 Agent Skill 设计质量的元技能，它依据官方规范和从 17+ 官方示例中提炼的模式，对 SKILL.md 文件进行多维度评分，并提供可操作的改进建议。

**核心定位**：一个综合性的评估框架，用于对照官方规范和最佳实践评估 Agent Skill 质量。

---

## 2. 核心哲学

### 2.1 Skill 的本质

> **Skill 不是教程，而是一种知识外化机制**。

传统的 AI 知识被锁定在模型参数中，要教授新能力需要：收集数据 → GPU 集群 → 训练 → 部署新版本，成本 $10,000-$1,000,000+，耗时数周到数月。Skill 改变了这一切：编辑 SKILL.md → 保存 → 下次调用即生效，成本 $0，即时生效。

这是从 **“训练 AI”到“教育 AI”** 的范式转变——就像一个可热插拔的 LoRA 适配器，无需训练。

### 2.2 核心公式

```
好 Skill = 专家专属知识 − 模型已知内容
```

Skill 的价值由它的 **知识增量**（knowledge delta）来衡量——即它提供的内容与模型已知内容之间的差距。

### 2.3 Skill 与 Tool 的区别

| 概念 | 本质 | 功能 | 示例 |
|------|------|------|------|
| **Tool** | 模型能做什么 | 执行动作 | bash, read_file, WebSearch |
| **Skill** | 模型知道如何做 | 指导决策 | PDF 处理, MCP 构建, 前端设计 |

Tool 定义能力边界，Skill 注入知识。

### 2.4 知识三分类

| 类型 | 定义 | 处理方式 |
|------|------|----------|
| **专家知识** | 模型确实不知道的内容 | **必须保留**——这是 Skill 的价值 |
| **激活知识** | 模型知道但可能不会主动想到 | 简短保留——作为提醒 |
| **冗余知识** | 模型确定知道的内容 | **应该删除**——浪费 Token |

---

## 3. 评估流程（5 步协议）

### 3.1 Step 1: 知识增量扫描（Knowledge Delta Scan）

通读整个 SKILL.md，将每个部分标记为“专家”、“激活”或“冗余”知识，计算知识比例（E:A:R）。

### 3.2 Step 2: 结构分析

检查：文件头格式是否正确、总行数、引用的参考文件列表及大小、遵循的设计模式、加载触发器。

### 3.3 Step 3: 逐项打分

针对 8 个维度逐一评分，为每个分数提供具体证据（引用原文）和理由。

### 3.4 Step 4: 计算总分与评级

汇总 8 个维度得分（满分 120 分），根据百分比给出 A 到 F 的最终评级。

### 3.5 Step 5: 生成报告

输出结构化评估报告，包含：总分、评级、知识比例、各维度得分、关键问题、前 3 项改进建议和详细分析。

---

## 4. 八大评估维度（120 分体系）

### D1: 知识增量（Knowledge Delta）— **20 分，核心维度**

| 分数 | 标准 |
|------|------|
| 0-5 | 解释模型已知的基础知识（“什么是 X”、标准库教程） |
| 6-10 | 混合：部分专家知识被明显内容稀释 |
| 11-15 | 大部分是专家知识，冗余极少 |
| 16-20 | 纯知识增量——每段话都物有所值 |

**危险信号**（得分 ≤5）：“什么是[基础概念]”章节、标准操作的分步教程、通用最佳实践。

### D2: 思维模式 vs. 操作步骤（Mindset vs. Mechanics）— **15 分**

考察 Skill 是传授专家级的思维框架，还是仅仅罗列机械的操作步骤。

### D3: 反模式质量（Anti-Pattern Quality）— **15 分**

评估 Skill 是否清晰地指出了“不要做什么”及其原因——这是区分专家和新手的重要标志。

### D4: 规范符合度（Specification Compliance）— **15 分**

检查 Skill 的 `description` 等元数据是否符合规范，是否清晰说明了“做什么”和“何时使用”。

### D5: 渐进式披露（Progressive Disclosure）— **15 分**

评估 Skill 是否采用分层设计——核心 SKILL.md 保持精简（建议 <300 行），详细文档放在 `references/` 按需加载。

### D6: 自由度校准（Freedom Calibration）— **15 分**

考察指令详细程度是否与任务易错程度相匹配。

### D7: 模式识别（Pattern Recognition）— **10 分**

检查 Skill 是否遵循已被验证的有效设计模式，而非从零发明一套方法。

### D8: 实用可用性（Practical Usability）— **15 分**

评估是否包含决策树、工作示例和边缘情况处理。

---

## 5. 常见失败模式识别

| 模式 | 症状 |
|------|------|
| **教程模式（The Tutorial）** | Skill 像一份入门教程，充满模型已知的基础知识 |
| **信息倾泻（The Dump）** | 所有信息塞进一个巨大的 SKILL.md，占满上下文窗口 |
| **模糊描述（The Vague Description）** | description 过于模糊，模型遇到相关问题时不激活 Skill |
| **复选框流程（The Checkbox Procedure）** | 沦为机械的步骤清单，没有决策原则或思维框架 |


# 文档三：Agent-Builder 技术白皮书

## 1. 概述

**Agent-Builder** 是一类元技能的统称，其核心目标是将**创建 AI 智能体**的过程从需要大量专业知识的复杂工程，转变为一种**标准化、可重复的自动化流程**。目前存在两种主流实现思路：

1. **预制工作流型**（如 `claude-agent-builder`）：将完整构建流程封装在提示词工作流中
2. **通用运行时型**（如 `builtbyV/agent-builder`）：提供本地优先、零依赖的智能体运行时

---

## 2. 思路一：预制工作流型（Claude Agent Builder）

### 2.1 核心定位

> **“把任何想法变成生产就绪的 AI 智能体”**

解决的核心问题：在 Claude Code 中构建智能体意味着要处理 **7 种不同原语**（subagents、skills、hooks、commands、MCP servers、CLAUDE.md、Agent SDK），每次都要从空白的 Markdown 文件开始。

### 2.2 六阶段自适应工作流

Agent Builder 在 **6 个阶段** 中运作，根据用户提供的上下文量自适应调整：

| 阶段 | 描述 |
|------|------|
| **CONTEXT SCAN** | 自动读取项目文件 + 对话历史 |
| **DISCOVERY** | 只询问 AI 无法从上下文推断出的关键信息 |
| **RESEARCH** | 并行搜索（GitHub + 博客 + 文档 + 社区）→ 整合简报 |
| **ARCHITECTURE** | 提出智能体架构方案，**构建前寻求用户明确批准** |
| **BUILD** | 将所有智能体文件直接写入项目目录 |
| **VERIFY** | 自我检查，展示构建结果，请求最终确认 |

### 2.3 与直接使用 Claude 的对比

| 维度 | 无 Agent Builder | 有 Agent Builder |
|------|------------------|------------------|
| 原语知识 | 需要了解全部 7 种原语 | 自动选择正确的原语 |
| 起点 | 从空白的 `.md` 文件开始 | 直接写入生产就绪文件 |
| 描述优化 | 猜测描述和工具 | 自动优化以触发 |
| 上下文 | 从头解释项目 | 自动扫描代码库和对话历史 |
| 调研 | 不知道已存在什么 | 搜索 GitHub、博客、文档和社区 |

### 2.4 关键特性

- **自适应**：用户提供的信息越多，需要问的问题就越少
- **并行研究**：同时在多个渠道搜索并整合
- **人类审批关口**：架构设计和最终验证阶段需要用户明确批准

---

## 3. 思路二：通用运行时型（builtbyV/agent-builder）

### 3.1 核心定位

> **“一个本地优先的智能体运行时。零依赖，一个文件，真正干活。”**

`agent.stub` 是一个完整的运行时，AI 编码助手将其转化为工作智能体。它处理执行循环：工具调度、轮次管理、上下文压缩、子智能体生成和安全门控。

### 3.2 核心能力矩阵

| 能力 | 描述 |
|------|------|
| **工具型智能体** | 文件、网络、API——任何内容 |
| **推理型智能体** | 分步问题解决 + 子智能体分解 |
| **自扩展智能体** | 运行时动态创建新工具 |
| **知识型智能体** | 从原始来源构建不断丰富的知识维基 |
| **技能驱动型智能体** | 将 `SKILL.md` 包放入 `./skills/`，按需加载 |
| **MCP 连接智能体** | 指向任何 MCP 服务器，工具自动可用 |
| **沙箱智能体** | 在 OCI 容器中运行不受信任的脚本 |

### 3.3 技术特性

- **零依赖**：仅需 Node.js 和 AI
- **渐进式披露的 Skills 支持**：按需加载 Skill，优化上下文使用
- **MCP 客户端**：支持 filesystem、GitHub、Postgres、Slack 等
- **容器沙箱**：通过 Apple 原生 `container` CLI 或 Docker 运行
- **内置 25 个工具**：开箱即用

### 3.4 工作模式

```
你描述想要什么 → AI 定制运行时 → 数秒内获得工作智能体
```

---

## 4. 两种思路对比

| 维度 | 预制工作流型 | 通用运行时型 |
|------|-------------|-------------|
| **目标用户** | Claude Code 用户 | 各类 AI 编码助手用户 |
| **产出物** | 完整的智能体文件集合 | 一个可运行的智能体实例 |
| **工作方式** | 多阶段自适应工作流 | 描述 → 定制 → 运行 |
| **扩展性** | 生成 7 种原语 | 25 个内置工具 + MCP |
| **依赖** | Claude Code 环境 | 仅 Node.js |

---

## 5. 技术精髓总结

| 维度 | 体现 |
|------|------|
| **自动化** | 从空白到生产就绪智能体，无需手写代码 |
| **自适应** | 根据上下文量动态调整提问和生成策略 |
| **标准化** | 固化最佳实践，封装 7 种原语的复杂性 |
| **本地优先** | 零依赖、单文件、无需云服务 |
| **可扩展** | MCP 协议 + Skills 机制，支持无限扩展 |
