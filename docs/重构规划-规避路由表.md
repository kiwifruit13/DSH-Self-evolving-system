# 规避洞察路由表：精简与进阶重构规划

> 目标：**实用与性能双提升**。以 `Gherkin.md`（行为契约）与 `总览.md`（架构定位）为标尺，
> 先纠偏、再精简、后接线、最后做性能。v1.0 · 2026-08-31

## 一、定位校准（规划的判据）

### 1.1 架构定位（总览.md）

- **CQRS 读写分离**：子代理（后台）独占写；主代理（前台）只读、秒级响应。
- **规避洞察路由表是四大核心数据资产之首**：树状错误分类 + 统计热力值 + 规避策略指针，
  每个节点绑定局部思维导图（边界 / 血缘 / 演化记述）。
- **受控自主**：根骨架由人类锁定，子节点由算法演化。

⇒ **推论**：路由表的任何"精简"都不能削弱三件事——
根骨架锁定、局部地图完整性、子代理写路径的可审计性。

### 1.2 三分类判据（取代上一轮的"用/没用"二分法）

上一轮以「生产代码是否调用」为判据，结论偏颇。改用契约判据：

| 类别 | 判据 | 处置 |
|---|---|---|
| **契约内·已接线** | Gherkin 场景直接依赖且代码已走通 | 保留 + 优化性能 |
| **契约内·未接线** | Gherkin 要求，但主/子代理没接上 | **接线，不删** |
| **契约外** | 总览与 Gherkin 均无对应 | 删除 |

### 1.3 重判结论

**由「待删」改判为「待接线」**

| API | 契约依据 | 现状 |
|---|---|---|
| `query_by_expression` | Gherkin F2 场景2「寻找最小代价方案」需 OR/NOT 语义 | `lookup_fuzzy()` 仅支持 AND |
| `rank_by="cost"` | 同上，「最小代价」即 cost 维度 | 零调用 |
| `orphan_audit` | 总览：局部地图完整性是核心执念 | 零调用，未接入巡检 |

**维持删除**

`bulk_upsert` / `bulk_create`（Step 47，零契约依据）、`EMPTY_STATS`（死常量）、
`inactive_days`（契约无对应）、`_check_sibling_overlap`（与 create_node 重复）、
`ScoreCalculator.rank/top_k`（与 RoutingTable 版本重复）。

**改判保留**

`delete_force` —— 无契约依据，但属运维能力。保留，标注为运维工具，移出核心语义。

### 阶段 A 完成记录

**A0 发现并修复「分裂功能实际是死代码」**
`maintain()` 的判据要求 `sample_count >= 5`，但三条建节点路径（蒸馏新建 / 蒸馏更新 /
反馈创建）与离线规划的 stats 中均无 `sample_count` 字段，该值恒为 0，分裂分支从不执行。
已为四条路径补齐初始化与递增。

**A1 分裂判据对齐 Gherkin F1 场景2**
判据由「单轮 top_k + sample_count」改为「连续 `split_consecutive` 次进入 Top N
**且**主导子类型占比 > `split_dominant_share` **且**样本数 ≥ `split_min_samples`」。
子节点名取样本中占比最高的子类型，取代原先 `focus.split()[-1][:20]` 的凭空截取。

**A2 子类型维度**
`DistilledFix` 新增 `subtype`（日志显式标注优先，回退到 `fix_action`——回退是必需的，
否则直方图恒空、判据重演失效）；`RoutingTableEntry` 以扁平前缀键维护观测直方图，
含名称清洗与容量上限淘汰。

**A3 连续计数跨轮维护**
`stats["top_streak"]`：进入 Top N 则 +1，落选归零。全表遍历更新（只遍历 Top N 会让
落选节点永不归零，「连续」退化成「累计」），且仅在值变化时落库。

**A4 分裂后状态重置**
分裂成功后重置 `top_streak` 并清除已分裂出的子类型计数，防止同一子类型无限分裂。
`RoutingTable.split()` 内部会重新读取父节点并 upsert，调用方持有的 entry 是过期副本，
故重置前必须重新读取，否则覆盖 split 写入的 `maintenance_log` 与 stats 重分配。

**A5 修复阈值取值不一致（D1）**

**验证**：新增 `tests/test_gherkin_scenarios.py`（11 项）；全量 377 项通过；
经变异测试确认「连续次数」「主导占比」两条判据均被真实覆盖（绕过任一条即失败）。

## 三、四阶段路线

> **顺序理由**：删代码前必须先确认契约，否则会误删"未接线"的能力；
> 性能基准必须在结构稳定后做，否则白测。

### 阶段 A：契约纠偏（正确性优先）

| 项 | 内容 |
|---|---|
| A1 | **分裂判据对齐 Gherkin F1 场景2**。契约：连续 3 次进入 Top3 **且** 子分类占比 > 70%。现状：单轮 `top_k` + `sample_count >= 5`，且 `child_name` 由 `focus.split()[-1][:20]` 凭空生成，与实际子类型分布无关 |

| A3 | 修 D1 阈值取值 bug（随 B3 删除 `_check_sibling_overlap` 一并解决） |

**验收**：补 Gherkin F1 场景2 的验收测试（连续 3 次 Top3 + 占比 >70% 才分裂；否则不分裂）。

**收益**：这是当前最高优先级——错误的分裂逻辑正在往核心资产里写入无意义子节点，
污染后续的 Skill 孵化与剪枝判定。其危害远大于任何性能损耗。

## 四、执行约束

1. **契约优先**：任何删除动作前，先在 Gherkin/总览中找到依据；找不到依据的先标记为
   "契约外·待确认"，不直接删。
2. **每阶段独立可回滚**：A/B/C/D 各一次提交，任一阶段失败不影响前一阶段。
3. **删代码必删测试**：精简阶段同步清理配套测试，否则测试/生产比会进一步失衡。
4. **修 bug 补回归**：D1-D5 每个缺陷修复后补对应回归测试。
5. **不动的根基**：四维打分 + 时间衰减、split/prune 自平衡闭环、`ROOT_CATEGORIES` 锁定层、
   `MAX_SPLIT_DEPTH`、`check`/`check_pair` 的语义分离（O(n³)→O(n²) 修正正确）。
