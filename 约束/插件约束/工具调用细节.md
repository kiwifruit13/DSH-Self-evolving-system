## 工具执行流水线：七阶段瀑布流全解

工具执行管线**不是**一个简单的前置/后置钩子对——它是一个七阶段瀑布流，具有严格的顺序不变量，可防止重排攻击并保证拒绝绝不会被后续的监听器逆转。

---

### 一、管线全景

从模型输出工具调用到冻结的 `tool/result`，完整流程如下：

```
assistant/message (含 tool_calls)
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  Stage 1: tool/call 记录                                 │
│  立即将调用意图追加到会话日志（即使后续拒绝，尝试仍被记录）    │
└─────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  Stage 2: 守卫检查（Monotonic Guards）                    │
│  注册表拥有的单调守卫，拒绝是绝对的——后续监听器无法逆转       │
└─────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  Stage 3: tools/pre-execute 瀑布流                       │
│  允许/拒绝/提问——审批提示词、沙箱策略在此集成               │
│  (waterfall 模式，必须调 next() 委托)                     │
└─────────────────────────────────────────────────────────┘
    │ 拒绝 → 短路至 Stage 7（规范化）
    ▼
┌─────────────────────────────────────────────────────────┐
│  Stage 4: tools/execute 瀭布流                           │
│  Around-dispatch：超时、重试、指标包装                     │
│  next() 运行工具主体；可替换 exec.signal 但不能改变调用身份  │
└─────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  Stage 5: 工具主体执行（Tool Body）                        │
│  实际的工具逻辑运行，可追加工具拥有的会话事件                  │
│  (todo/write, fs/observed, hook/invoked, hook/result 等)  │
└─────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  Stage 6: tools/post-execute 瀑布流                      │
│  接受/替换/丰富/阻止已规范化的结果                          │
│  即使工具抛出异常，仍会到达此阶段                           │
└─────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  Stage 7: 规范化 + deepFreeze + 日志追加 + 事件发布        │
│  → session.append('tool/result', ...)                    │
│  → ctx.emit('tools/result', exec, frozenResult)          │
│  → UI.presentResult(args, result)                        │
└─────────────────────────────────────────────────────────┘
```

---

### 二、逐阶段详解

#### Stage 1：tool/call 记录

**立即**追加一个 `tool/call` 会话事件到日志。这保证了每次尝试的调用都是持久化的——即使管线随后拒绝了它，会话日志也捕获了该**意图**。

```typescript
session.append('tool/call', {
  turn, step, callId, name, arguments
})
```

同时，UI 通过工具的 `presentCall(args)` 方法接收一个待处理状态的卡片。`callId` 将此事件与后续的 `tool/result` 配对。

#### Stage 2：守卫检查（Monotonic Guards）

守卫是注册表拥有的**单调**拒绝机制。与 `tools/pre-execute` 监听器不同：

| | 守卫（Guard） | pre-execute 监听器 |
|---|---|---|
| 拒绝性质 | **绝对**——不可被后续监听器逆转 | **可重排**——后续监听器可能绕过 |
| 安全关键逻辑 | ✅ 应放此处 | ❌ 不应放此处 |
| 注册方式 | 工具注册时声明 | `ctx.on('tools/pre-execute', fn)` |

> **关键安全原则**：安全关键的拒绝逻辑应始终实现为守卫，而非 `tools/pre-execute` 监听器。pre-execute 的拒绝可通过监听器重排攻击规避；守卫的拒绝是绝对的。

#### Stage 3：tools/pre-execute 瀑布流

```typescript
ctx.on('tools/pre-execute', (exec, next) => {
  // exec 包含：name, parsed arguments, caller agent, signal
  // 决策：allow / deny / ask
  return next()  // 委托给下一个监听器
})
```

**派发模式**：waterfall（Cordis 事件），监听器按注册顺序运行，每个必须调用 `next()` 以委托给下一个。

**返回值**（`PreToolDecision`）：
- **allow**：继续进入 Stage 4
- **deny**：短路至 Stage 7，生成拒绝结果
- **ask**：触发审批提示词；若缺少审批支持则退化为 deny

**在此集成的策略**：
- 沙箱模式检查（`ctx.sandboxPolicy`）——决定是否允许写入类操作
- 审批提示词（`ctx.approval.request()`）——需要用户确认的危险操作
- 异步门控必须观察 `exec.signal`；注册表在它们 settle 后重新检查取消状态

**作用域过滤**：Agent 作用域的监听器仅接收该 Agent 的调用——多 Agent 进程的工具策略独立运行，无交叉污染。

#### Stage 4：tools/execute 瀑布流

```typescript
ctx.on('tools/execute', (exec, next) => {
  // Around-dispatch：包装工具主体的执行
  // 可替换 exec.signal（超时/取消），但调用身份不可变
  return next()  // 运行工具主体
})
```

**用途**：超时包装、重试逻辑、指标收集。

**关键约束**：注册表在工具主体运行前**重新融合**原始调用者的 signal，所以包装器替换 signal 无法脱离调用者取消；包装器必须在自身清理时恢复 signal 并到达静止。

#### Stage 5：工具主体执行

这是实际的工具逻辑运行阶段。工具主体接收已解析的参数和执行上下文，返回 `ToolExecutionResult`。

工具主体在执行期间还可以追加**工具拥有的会话事件**——这些是持久化日志条目，但**不会重新进入模型上下文**：

| 事件 | 用途 |
|---|---|
| `todo/write` | 待办列表更新 |
| `fs/observed` | 文件系统观察记录 |
| `hook/invoked` / `hook/result` | 钩子协议事件 |
| `tool/code-dispatch-start` / `tool/code-dispatch` | Code Mode 子调度事件 |

#### Stage 6：tools/post-execute 瀑布流

```typescript
ctx.on('tools/post-execute', (exec, result, next) => {
  // result 是已规范化的派发结果
  // 决策：accept / replace / enrich / block
  return next()  // 接受不变
})
```

**重要**：即使工具抛出异常，仍会作为错误结果到达此阶段——post-execute 无法跳过。

**返回值**（`PostToolDecision`）：
- **accept**：接受原结果
- **replace**：替换结果内容（如溢出策略用预览+定位器替换超大文本）
- **enrich**：丰富结果（添加额外上下文）
- **block**：阻止结果到达模型

异步监听器必须观察 `exec.signal`；调用者取消只能替换成功的已接受结果。

#### Stage 7：规范化 + 冻结 + 持久化

最终阶段执行三件事：

1. **内容规范化**：将工具主体返回的原始结果规范化为 `tool/result` 的标准格式
2. **深度冻结**：`deepFreeze(result)` ——结果从此不可变
3. **日志追加 + 事件发布**：

```typescript
// 持久化到会话日志
session.append('tool/result', {
  turn, step,
  message: ToolResultMessage,
  error?: { name, code },
  meta?: JsonValue       // 工具私有的展示负载
}, { surfaceOp: 'append', sourceEventSeqs: [...] })

// 同步通知观察者（emit 模式，失败隔离）
ctx.emit('tools/result', exec, frozenResult)

// UI 渲染完成状态卡片
presentResult(args, result)
```

`meta` 字段是工具私有的展示负载——对核心不透明，但必须 JSON 可序列化。例如 `dsh-tool-fs` 在此处携带结果时间的上下文差异卡片。

### 三、拒绝与短路的顺序不变量

```
                    ┌─ 守卫拒绝 ────────┐
                    │                    │
Stage 1 ──► Stage 2 ──► Stage 3 ──► Stage 4 ──► Stage 5 ──► Stage 6 ──► Stage 7
                    │         │                                      ▲
                    │         └─ pre-execute 拒绝 ──────────────────┘
                    └──────────────────────────────────────────────┘
                          (所有拒绝短路至规范化阶段)
```

**顺序不变量**：
1. 守卫先于 pre-execute 运行——守卫拒绝不可被 pre-execute 覆盖
2. pre-execute 先于 execute 运行——拒绝的调用不进入工具主体
3. post-execute 在主体完成后运行——即使异常也到达
4. 规范化始终最后——保证输出的 `tool/result` 是冻结的、无损 JSON 的

### 四、Code Mode 子调度管线

当工具在 Code Mode（`run_code`）下运行时，子调度有额外的管线事件：

| 事件 | 用途 | 模型可见？ |
|---|---|---|
| `tool/code-dispatch-start` | 子调度开始（含 `rootCallId`、`parentCallId`、`subCallId`） | 否（仅日志） |
| `tool/code-dispatch` | 子调度完成（含完整 `content` + `isError`） | 否（仅日志） |

子调度的 `subCallId` 格式为 `<parent>:code:<n>`，按提交顺序编号。还有一个专用的瀑布流事件 `tools/code-dispatch-log`，允许监听器在桥接追加 `tool/code-dispatch` 事件前替换持久日志副本中的内容（如溢出策略）——但程序本身已收到完整值，模型也看不到替换。

---

### 五、事件键控与作用域隔离

- `tools/result` 发射事件由 `exec.agent` 键控——多 Agent 进程中每个 Agent 的工具策略独立运行
- `tools/change` 事件**不过滤**——全局注册表变更影响每个 Agent 的下一次提示词组装，所以作用域监听器能看到所有变更
- 守卫和瀑布流监听器均受作用域过滤分发约束

### 六、架构总结表

| 关注点 | 机制 | 事件 |
|---|---|---|
| 调用意图持久化 | `session.append('tool/call')` | `tool/call` |
| 安全绝对拒绝 | 单调守卫 | —（内部） |
| 审批/策略拦截 | `tools/pre-execute` 瀑布流 | `tools/pre-execute` |
| 超时/重试/指标 | `tools/execute` 瀑布流 | `tools/execute` |
| 结果后处理 | `tools/post-execute` 瀑布流 | `tools/post-execute` |
| 结果持久化 | `session.append('tool/result')` | `tool/result`, `tools/result` |
| UI 渲染 | `presentCall` / `presentResult` | — |
