插件开发用户最常用的领域，按使用频率从高到低排列，共六大领域。

---

## 一、工具注册与实现 — 最核心的扩展点

这是绝大多数插件开发者的第一需求：让模型获得新能力。

```typescript
ctx.tools.register({
  name: 'my_tool',
  description: '...',
  parameters: { ... },        // JSON Schema
  execute: async (args, exec) => { ... },
  presentCall: (args) => ...,  // UI 待处理卡片
  presentResult: (args, result) => ..., // UI 完成卡片
})
```

**常用关注点**：
- `name` / `description` / `parameters`：决定模型如何发现和调用
- `execute` 主体：实际逻辑，可追加工具拥有的会话事件（`todo/write`、`fs/observed` 等）
- `output.schema` + `output.render`：程序化消费者先设计 schema，模型可见文本由 render 处理
- `presentCall` / `presentResult`：UI 渲染，与模型结果解耦
- 守卫（`guards`）：安全关键拒绝逻辑，绝对不可绕过

卸载时自动从注册表移除，无需手动清理。

---

## 二、事件监听 — 横切关注点的首选手段

```typescript
ctx.on('agent/pre-step', (exec, next) => { ... return next() })
ctx.on('tools/pre-execute', (exec, next) => { ... return next() })
ctx.on('session/event', (session, event) => { ... })
```

**最常监听的事件域**：

| 事件域 | 典型用途 | 派发模式 |
|---|---|---|
| `agent/pre-step` | 步骤前拦截/修改 | waterfall |
| `agent/request` | 请求拦截/转换 | waterfall |
| `agent/turn-stopping` | 轮次停止拦截 | waterfall |
| `tools/pre-execute` | 审批、沙箱策略 | waterfall |
| `tools/post-execute` | 结果后处理 | waterfall |
| `tools/result` | 观察冻结结果 | emit |
| `session/event` | 持久化、遥测 | emit |
| `session/flush` | 持久性检查点 | parallel |

**注意**：waterfall 事件忘记 `next()` 是最常见的 bug；`emit` 事件不可拦截。

---

## 三、服务提供与消费 — 可替换能力的实现

```typescript
// 提供
ctx.provide('myService', new MyServiceImpl())

// 消费
ctx.inject(['myService'], (myService) => {
  // 依赖就绪后运行；服务替换时自动重新加载
})
```

**常见的服务键**：

| `ctx` 键 | 用途 | 常见替换场景 |
|---|---|---|
| `ctx.tools` | 工具注册表 | — |
| `ctx.llm` | LLM 适配器注册 | 切换模型提供者 |
| `ctx.fs` | 文件系统操作 | 本地 → 远程沙箱 |
| `ctx.shell` | Shell 执行 | 本地 → 沙箱 |
| `ctx.sandbox` | 沙箱后端 | 切换隔离策略 |
| `ctx.sessions` | 会话存储 | — |
| `ctx.systemPrompt` | 系统提示词组装 | — |

**替换一个提供者就能改变整个产品**：将 `ctx.fs` 指向远程沙箱，bash、PTY、LSP 自动跟随。

---

## 四、系统提示词与上下文注入 — 引导模型行为

```typescript
// 注册提示词片段（自动加入系统提示词组装）
ctx.systemPrompt.register('my-guidance', {
  text: 'Always respond in JSON',
  order: 110,  // 100-199: 每工具指导区间
})

// 运行时注入上下文（下一次请求生效）
agent.inject({ role: 'user', content: '...' })
```

**常见用法**：
- 人设（persona）：Agent 身份描述，`complete: true` 可独占系统提示词
- 工具指导：每个工具的使用说明（100-199 顺序区间）
- 运行时上下文快照：沙箱模式、审批策略等动态状态
- `agent.inject()`：在运行时向 Agent 的收件箱注入消息，下一次获准请求时生效

---

## 五、LLM 适配器注册 — 接入新模型提供者

```typescript
ctx.llm.register('my-provider', myAdapter)
```

**常用关注点**：
- 适配器实现 `LlmAdapter` 接口（流式生成）
- 路由解析：`provider` + `model` → 适配器实例
- `llm/stream` 瀑布流：请求拦截/指标/日志
- 重复路由抛异常；多路由全有或全无
- 循环组装的请求深度冻结（只读），手工构建的请求可在应用层修改

## 六、会话事件扩展与投影 — 持久化自定义状态

```typescript
// 扩展事件词汇表（declaration merging）
declare module '@deepseek-ai/dsh-session/types' {
  interface SessionEventMap {
    'my-plugin/state': { ... }
  }
}

// 注册投影（CQRS 读模型）
ctx.on('session/event', (session, event) => {
  if (event.type === 'my-plugin/state') { ... }
})
```

**常见用法**：
- 添加工具拥有的会话事件（`ignorable: true`，旧运行时可安全跳过）
- 注册命名投影（`session-projection`），增量维护派生状态
- 持久化插件：订阅 `session/event` 缓冲，`session/flush` 排空

## Cordis 插件教程：从零到注册真正工具的完整演练

教程共七步，从一个 hello world 函数逐步进阶到完全集成 Harness 工具执行管线的插件。每一步建立在前一步之上，最终掌握五个 Cordis 核心理念。

---

### 前置：五大核心理念

| 理念 | 描述 |
|---|---|
| **插件即服务** | 插件实现 `Service`——带 `inject` 和 `apply(ctx)` 的函数或 `Service` 子类，Cordis 挂载其生命周期 |
| **上下文即仓库** | 服务声明 `ctx.<key>`，其他插件通过键发现，从不导入具体实现 |
| **通过 inject 注入依赖** | 声明所需服务，等待其就绪；加载顺序由依赖决定，非手动排序 |
| **类型化事件** | 通过声明合并声明事件名，以 `emit`/`waterfall`/`parallel`/`serial` 派发 |
| **可逆效应** | 注册项通过 `ctx.effect()` 或 `ctx.on()` 安装，重载和卸载时自动撤销 |

---

### 步骤 1 — 编写你的第一个插件

在 Cordis 加载器配置中，插件模块通过**命名导出**一个 `apply` 函数：

```typescript
// hello.ts
export function apply(ctx: Context) {
  console.log('hello from plugin')
}
```

```yaml
# cordis.yml
plugins:
  - name: './hello.ts'
```

启动器创建根 `Context`，挂载 Loader 插件，从 `./cordis.yml` 加载配置。调用流程：

```
bin.js → 创建根 Context → 挂载 Loader → 解析 cordis.yml → 加载 ./hello.ts → 调用 apply(ctx)
```

**关键**：`apply` 是插件唯一的入口。Cordis 调用它时，fiber 从 `PENDING` 转换至 `LOADING`，`apply` 完成后转为 `ACTIVE`。

---

### 步骤 2 — 使用 Effects 管理生命周期

插件可因配置编辑、热重载、显式释放或服务丢失而被**卸载**。`ctx.effect()` 注册一个副作用，其返回的清理函数在卸载时按注册逆序运行：

```typescript
export function apply(ctx: Context) {
  const timer = setInterval(() => console.log('tick'), 1000)

  ctx.effect(() => {
    console.log('heartbeat plugin loading')
    return () => {
      console.log('heartbeat cleaned up')
      clearInterval(timer)
    }
  })
}
```

**执行顺序**：
1. 加载时：`heartbeat plugin loading` → `tick tick tick...`
2. 卸载时：`heartbeat cleaned up` → `disposed`

**核心规则**：
- 清理函数按注册的**逆序**启动
- 多个**异步**清理函数会**并发**运行
- 如果拆卸步骤必须有序，保留在同一个清理函数中依次 `await`

```typescript
// 顺序异步清理
ctx.effect(() => {
  return async () => {
    await closeDatabase()
    await flushLogs()
  }
})
```

**但大多数时候你不需要 `ctx.effect()`**——内置 API 本身就是副作用：

| 注册项 | 卸载时自动清理 |
|---|---|
| `ctx.on(event, listener)` | 监听器被移除 |
| `ctx.plugin(child)` | 子插件随父插件一同释放 |
| `ctx.provide(name, impl)` | 服务被注销 |
| `ctx.tools.register(...)` | 工具被注销 |

---

### 步骤 3 — 通过服务共享能力

**服务**是一个插件提供、其他插件通过 `ctx` 消费的能力：

```typescript
// stats.ts — 服务提供者
export class StatsService extends Service {
  private counts = new Map<string, number>()

  increment(name: string) {
    const next = (this.counts.get(name) ?? 0) + 1
    this.counts.set(name, next)
    this.ctx.emit('stats/report', name, next)
  }
}

export const name = 'stats'
export function apply(ctx: Context) {
  ctx.plugin(StatsService)
}
```

```typescript
// greeter.ts — 服务消费者
export const inject = ['stats']

export function apply(ctx: Context) {
  ctx.on('message', (name) => {
    ctx.stats.increment(name)  // 通过 ctx 键发现服务
  })
}
```

**服务发现**：消费者声明 `inject: ['stats']`，Cordis 确保服务就绪后才激活插件。若服务消失（提供者被卸载），依赖它的插件也会卸载；服务重新出现时再次加载——这就是**热替换**的机制。

---

### 步骤 4 — 通过类型化事件通信

服务支持直接调用；**事件**让插件在不知晓哪些插件监听的情况下发布通知。

```typescript
// 声明事件签名（declaration merging）
declare module '@deepseek-ai/cordis' {
  interface Events {
    'stats/report'(name: string, count: number): void
  }
}
```

声明后，`ctx.emit` 和 `ctx.on` 获得完整类型支持：

```typescript
// 生产者
ctx.emit('stats/report', name, count)  // 类型安全

// 消费者
ctx.on('stats/report', (name, count) => {
  console.log(`${name}: ${count}`)  // 参数自动推断
})
```

**五种派发模式**：

| 模式 | 等待？ | 顺序 | 返回值？ | 典型用途 |
|---|---|---|---|---|
| `emit` | 否 | 并发 | 否 | 通知、日志 |
| `waterfall` | 是 | 串行，必须调 `next()` | 是 | 拦截/转换管道 |
| `serial` | 是 | 串行，首个决定 | 是 | 首个持有立场者决定 |
| `parallel` | 是 | 并发 | 是 | 等待所有完成 |
| `truncate` | 否 | 并发 | 否 | 事件截断 |

**⚠️ 最常见的 bug**：waterfall 事件忘记 `next()` 会静默吞没所有下游监听器的默认行为。

---

### 步骤 5 — 添加经校验的配置

每个 `cordis.yml` 条目可携带 `config` 块，插件声明 schema 校验：

```yaml
plugins:
  - name: './greeter.ts'
    config:
      greeting: "Hello"
      interval: 5000
```

```typescript
import z from '@deepseek-ai/schemastery'

export const Config = z.object({
  greeting: z.string().default('Hello'),
  interval: z.number().default(5000),
})

export function apply(ctx: Context, config: z.infer<typeof Config>) {
  console.log(config.greeting)  // 类型安全，已校验
}
```

**配置条目元数据**：

```yaml
- id: greeter          # 稳定标识（HMR 追踪用）
  name: './greeter.ts'
  disabled: false       # 可禁用
  config: { ... }
```

Cordis 在 fiber 从 `PENDING` 转换至 `LOADING` 前校验配置。校验失败 → `FAILED` 状态，`apply` 不会运行。

---

### 步骤 6 — 组合、HMR 与诊断

**组合**：`ctx.plugin(child)` 将子插件挂载到父插件——子 fiber 随父 fiber 一同销毁：

```typescript
export function apply(ctx: Context) {
  ctx.plugin(heartbeatPlugin)
  ctx.plugin(statsPlugin)
  // 卸载时两者自动销毁，逆序清理
}
```

**HMR（热模块替换）**：修改插件源码 → Cordis 卸载旧 fiber → 加载新 fiber。`cordis.patch.yml` 支持运行时打补丁，无需重启。

**诊断 PENDING 状态**：如果插件没有任何输出，检查 `inject`——fiber 可能在等待尚未提供的服务。这是**正确行为**；依赖出现后自动激活。

**Fiber 状态机全貌**：

```
PENDING ──(依赖就绪)──▶ LOADING ──(apply 完成)──▶ ACTIVE
   │                       │                        │
   │                       │(apply 抛错)             │(dispose / 服务消失)
   │                       ▼                        ▼
   │                    FAILED                  UNLOADING ──▶ DISPOSED
   │
   └─(依赖永不到达)= 永远 PENDING（正确，不报错）
```

---

### 步骤 7 — 注册真正的 Harness 工具

最后一步向 Harness 的 `tools` 服务注册一个可供模型调用的工具，通过执行管线执行，并观察结果事件：

```typescript
import { ToolRuntime } from '@deepseek-ai/dsh-tools'

export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.tools.register({
    name: 'my_echo',
    description: 'Echo back the input text',
    parameters: {
      type: 'object',
      properties: {
        text: { type: 'string', description: 'Text to echo' }
      },
      required: ['text']
    },
    async execute(args, exec) {
      return {
        content: [{ type: 'text', text: args.text }],
      }
    },
  })
}
```

**执行路径**：模型调用 `my_echo` → 七阶段管线 → `execute` 主体运行 → 结果规范化 → `tool/result` 事件 → UI 渲染。

**两个插件协作示例**：一个提供者注册工具，一个消费者监听结果——彼此不知对方存在，注册表和事件将它们连接：

```typescript
// 消费者：观察工具结果
ctx.on('tools/result', (exec, result) => {
  if (exec.name === 'my_echo') {
    console.log('echo completed:', result)
  }
})
```

> 一个真正的 Agent 就是这种组合再加上更多插件：LLM 适配器、Agent 循环、持久化、入口点。

## 服务与依赖注入：ctx 键系统与服务解析

框架的依赖注入系统确保消费者仅在所有必需服务可用时才会激活，并自动级联生命周期变更（包括热替换），无需手动连接或协调加载顺序。

---

### 一、服务三角色

每个能力接缝都由三个角色协同完成，彼此通过 `ctx` 键和 `inject` 解耦：

| 角色 | 职责 | 示例 |
|---|---|---|
| **服务定义** | 声明接口和 `ctx.<key>` 键 | `dsh-fs` 声明 `ctx.fs` — 文件系统操作 |
| **服务提供者** | 实现接口并在键上注册 | `fs-local`、`fs-sandbox`、`fs-e2b` |
| **消费者** | 通过键使用服务 | `tool-fs`、`bash-local`、`lsp-local` |

**核心原则**：消费者通过键发现服务，**从不导入具体实现**。替换一个提供者就能改变整个产品——将 `ctx.fs` 指向远程沙箱，bash、PTY、LSP 自动跟随。

---

### 二、服务注册：`ctx.provide()` 与 `Service` 类

#### 函数形态（最常见）

```typescript
export function apply(ctx: Context) {
  ctx.provide('myService', myServiceImpl)
}
```

函数形态用于不需要暴露服务自身方法的场景——注册后消费者直接通过 `ctx.myService` 访问实现对象。

#### 类形态（需要方法与生命周期）

```typescript
export class StatsService extends Service {
  private counts = new Map<string, number>()

  constructor(ctx: Context) {
    super(ctx, 'stats')  // 键名传给 Service 基类
  }

  increment(name: string) {
    const next = (this.counts.get(name) ?? 0) + 1
    this.counts.set(name, next)
    this.ctx.emit('stats/report', name, next)
  }
}

export const name = 'stats'
export function apply(ctx: Context) {
  ctx.plugin(StatsService)  // 挂载为子插件，自动注册到 'stats' 键
}
```

类形态的用武之地：服务需要暴露方法供消费者直接调用（`ctx.stats.increment()`），且需要自己的内部状态和生命周期。

#### 注册的完整流程

1. **存储到 reflect 注册表** — `reflect.provide(name, impl, fiber)` 将实现存入全局反射存储
2. **安装到上下文代理** — `ctx[name] = impl`，使 `ctx.myService` 直接可访问
3. **存入 fiber.store** — 快速依赖检查用
4. **通知依赖方** — 若提供纤程已为 ACTIVE，`reflect.notify([name])` 重新评估所有注入 `name` 的纤程
5. **返回清理器** — 清理时从两个存储中移除服务并通知依赖方

---

### 三、依赖声明：`inject` 字段

```typescript
export const inject = ['tools', 'sessions']

export function apply(ctx: Context) {
  // 此时 ctx.tools 和 ctx.sessions 保证可用
  ctx.tools.register({ ... })
}
```

**解析规则**：Cordis 调用 `_getImpl(name, true)` 寻找既已注册且提供纤程为 **ACTIVE** 的实现。若缺少任何依赖，纤程保持 **PENDING**——`apply` 根本不会运行。

这是有意为之的设计——它**取消手动引导排序**，转而采用依赖驱动的激活方式。

---

### 四、ctx 代理与解析路径

`ctx` 是一个 Proxy 对象。当你访问 `ctx.tools` 时，代理执行以下游走：

```
ctx.tools
    │
    ▼
当前纤程的 fiber.store 中查找 'tools'
    │
    ├─ 找到且提供纤程 ACTIVE ──▶ 返回实现
    │
    ├─ 未找到 ──▶ 游走至父纤程的 store
    │              │
    │              ├─ 找到且 ACTIVE ──▶ 返回实现
    │              └─ 继续向上 ...
    │
    └─ 全链未找到
         │
         ├─ 是 inject 声明的必需服务？
         │    ├─ 是 ──▶ 抛出异常：非活动上下文中的必需服务
         │    └─ 否 ──▶ 返回 undefined（可选服务）
         │
         └─ 纤程保持 PENDING
```

**关键属性**：

- 此游走确保上下文仅解析其**自身隔离作用域**内的服务
- 必需服务缺失时**抛出信息丰富的错误**，而非返回 `undefined`——防止插件假定服务存在但未声明依赖而导致的静默失败
- 可选服务（未在 `inject` 中声明）返回 `undefined`，插件需自行检查

---

### 五、热替换与级联生命周期

当某个必需服务在运行时消失——其提供者被卸载或热替换——依赖图发生级联：

```
提供者被卸载（如 dsh-bash-local）
    │
    ▼ reflect.notify(['shell'])
重新评估所有注入 'shell' 的纤程
    │
    ▼
每个依赖纤程 → UNLOADING → DISPOSED
    │
    ▼ 新提供者挂载（如 dsh-bash-sandbox）
reflect.notify(['shell'])
    │
    ▼
每个依赖纤程 → PENDING → LOADING → ACTIVE（针对新实现重新加载）
```

**这正是配置中服务替换得以生效的机制**：卸载一个 `shell` 提供者条目，挂载另一个，每个注入 `'shell'` 的插件都会**干净地针对新实现重启**，不留任何陈旧引用。

---

### 六、ctx.inject() — 动态依赖回调

除了静态的 `inject` 字段，还有运行时的 `ctx.inject(deps, callback)`：

```typescript
ctx.inject(['llm', 'tools'], (llm, tools) => {
  // 依赖就绪后运行
  // 依赖变更时自动卸载旧回调并重新运行
})
```

与 `inject` 字段的区别：
- `inject` 字段：控制 `apply` 是否运行（纤程级）
- `ctx.inject()`：在 `apply` 内部注册动态依赖回调，依赖变更时**回调重新运行**而非整个插件重新加载

### 八、internal/set 与 internal/get 瀑布流

服务读写本身也通过事件系统，允许拦截：

| 事件 | 模式 | 用途 |
|---|---|---|
| `internal/set` | waterfall | 通过上下文代理写入服务时可拦截 |
| `internal/get` | waterfall | 通过上下文代理读取服务时可拦截 |

这使得插件可以在服务解析过程中注入横切逻辑——如权限检查、审计日志、懒加载代理等——而无需修改服务定义或提供者。

### 九、架构原则总结

| 原则 | 含义 |
|---|---|
| **键即契约** | `ctx.<key>` 是稳定的公共 API；实现可替换，键不可变 |
| **依赖驱动激活** | 无需手动引导排序；`inject` 声明即足够 |
| **级联生命周期** | 服务消失 → 依赖方卸载；服务重现 → 依赖方重新加载 |
| **作用域隔离** | 游走仅限当前作用域；多 Agent 进程各自独立 |
| **静默失败防护** | 必需服务缺失时抛错而非返回 undefined |
| **可逆注册** | `provide` 返回清理器；卸载时自动移除并通知 |

## 添加工具与适配器：完整形态、契约与表现层

两条接缝遵循相同的 Cordis 插件契约：声明名称，注入注册表服务，在 `apply()` 中注册。销毁纤程自动注销贡献，构造上即满足 HMR 安全与生命周期正确。

---

### 一、工具注册：从最小到完整形态

#### 最小形态

```typescript
import { defineTool } from '@deepseek-ai/dsh-tools'

export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.tools.register(defineTool({
    name: 'my_echo',
    description: 'Echo back the input text',
    parameters: {
      type: 'object',
      properties: {
        text: { type: 'string', description: 'Text to echo' }
      },
      required: ['text']
    },
    async execute(args, exec) {
      return {
        content: [{ type: 'text', text: args.text }],
      }
    },
  }))
}
```

`defineTool` 辅助函数提供完整类型推导、自动参数校验和模式编译。

#### 完整形态——所有字段

| 字段 | 类型 | 用途 | 约束 |
|---|---|---|---|
| `name` | `string` | 模型寻址的唯一标识符 | 注册表中必须唯一 |
| `description` | `string` | 模型在系统提示词中读取的文本 | 简明扼要、面向动作 |
| `parameters` | JSON Schema | 模型生成的调用参数结构 | 必须是合法 JSON Schema |
| `execute` | `(args, exec) => Promise<ToolResult>` | 工具主体 | 见契约章节 |
| `output.schema` | JSON Schema | 程序化返回值结构 | Code Mode 消费者使用 |
| `output.render` | `(value) => string` | 面向模型的文本渲染 | 纯函数，无 I/O |
| `presentCall` | `(args) => ToolCallView` | UI 待处理状态卡片 | 纯函数 |
| `presentResult` | `(args, result) => ToolResultView` | UI 完成状态卡片 | 纯函数 |
| `guards` | `Guard[]` | 单调守卫列表 | 拒绝绝对不可绕过 |
| `concludesTurn` | `boolean` | 结果是否终结轮次 | 不短路已提交的 next-step |

---

### 二、工具契约——必须遵守的规则

#### 契约 1：execute 主体

```typescript
async execute(args, exec): Promise<ToolExecutionResult>
```

- `args`：已解析和校验的参数（`defineTool` 自动校验）
- `exec`：执行上下文，包含 `exec.agent`（调用方 Agent）、`exec.session`（会话）、`exec.signal`（取消信号）

**主体运行期间可追加工具拥有的会话事件**（不进入模型上下文）：

| 事件 | 用途 |
|---|---|
| `todo/write` | 待办列表更新 |
| `fs/observed` | 文件系统观察记录 |
| `hook/invoked` / `hook/result` | 钩子协议事件 |
| `tool/code-dispatch-start` / `tool/code-dispatch` | Code Mode 子调度 |

#### 契约 2：输出分离原则

**程序化消费者先设计 `output.schema`，模型可见文本由 `output.render` 处理**：

```typescript
defineTool({
  name: 'read_file',
  // ...
  output: {
    schema: {                       // Code Mode 程序化消费者
      type: 'object',
      properties: {
        content: { type: 'string' },
        lines: { type: 'number' }
      }
    },
    render: (value) => value.content  // 模型读取的文本
  },
  async execute(args, exec) {
    const content = await readFile(args.path)
    return { content, lines: content.split('\n').length }
  }
})
```

中间值是执行局部的，不被持久化或提示词截断，也没有字节上限——仅有渲染后的面向模型内容受预算限制。

#### 契约 3：表现层纯净性

- `presentCall` 和 `presentResult` 必须是 `args`（+ 结果）的**纯函数**——无 I/O、不读取会话状态、不依赖时钟/随机数
- **仅用于 UI 的格式化不应混入模型结果**：围栏 ` ```console ` 块、差异对比、相对化路径——不属于规范值
- `output.render` 掌管面向模型的文本；`presentationMeta` + 卡片表现器掌管可重放的 UI 元数据
- `defineTool` **软校验**显示路径：畸形或较旧的已记录参数使包装器返回 `undefined`（通用回退）而非抛异常——**显示绝不能导致重放崩溃**

#### 契约 4：concludesTurn 语义

设置 `concludesTurn: true` 的工具结果**不会**短路已提交的 `next-step` 工作——同步骤的 `additionalContexts` 或竞争的引导仍会执行，轮次仅在收件箱排空后关闭。此设计确保工具产生的上下文不会被静默丢弃。

### 三、表现层：卡片视图系统

表现层将工具执行连接到 UI，有两种卡片：

#### presentCall — 待处理卡片

```typescript
presentCall: (args) => ({
  kind: 'generic',     // | 'terminal' | 'diff'
  title: `Reading ${args.path}`,
  // ...kind-specific fields
})
```

#### presentResult — 完成卡片

```typescript
presentResult: (args, result) => ({
  kind: 'generic',     // | 'terminal' | 'diff' | 'search' | 'read' | 'web'
  title: `Read ${args.path}`,
  // ...kind-specific fields
})
```

**卡片类型词汇**：

| `ToolCallView` kind | `ToolResultView` kind | 用途 |
|---|---|---|
| `generic` | `generic` | 通用文本展示 |
| `terminal` | `terminal` | Shell/PTY 输出 |
| `diff` | `diff` | 文件差异对比 |
| — | `search` / `searchMatches` / `searchPaths` | 搜索结果 |
| — | `read` | 文件读取结果 |
| — | `web` / `webSearch` / `webFetch` | Web 搜索/抓取 |

中性词汇位于 `dsh-tools` 中；工具**绝不**导入 UI 或传输类型。

### 四、守卫：安全关键的绝对拒绝

守卫在工具执行管线的 Stage 2 运行，先于 `tools/pre-execute` 瀑布流：

```typescript
defineTool({
  name: 'write_file',
  // ...
  guards: [
    {
      name: 'path-traversal',
      check: (args, exec) => {
        if (args.path.includes('..')) return { decision: 'deny', reason: 'Path traversal' }
        return { decision: 'allow' }
      }
    }
  ],
  // ...
})
```

| | 守卫 | pre-execute 监听器 |
|---|---|---|
| 拒绝性质 | **绝对**——后续监听器无法逆转 | **可重排**——可被绕过 |
| 运行时机 | Stage 2（最先） | Stage 3（守卫之后） |
| 适用场景 | 路径遍历防护、权限硬拒绝 | 审批提示词、沙箱策略 |

### 五、LLM 适配器：完整形态

#### 最小形态

```typescript
export const inject = ['llm']

export function apply(ctx: Context) {
  ctx.llm.register('my-provider', {
    async *stream(options) {
      // 实现 LlmAdapter 契约
      const response = await fetch('https://api.my-provider.com/v1/chat/completions', {
        method: 'POST',
        headers: {
          'Content-Type': 'application/json',
          ...attributionHeaders(),  // 归因标头——注册中心强制执行
        },
        body: JSON.stringify(options)
      })
      // 解析 SSE 流，yield StreamChunk
    }
  })
}
```

#### 适配器契约

| 契约 | 含义 |
|---|---|
| **归因标头** | HTTP 请求**必须**包含 `attributionHeaders()`，注册中心强制执行 |
| **路由唯一** | 每个提供商路由对应一个适配器——重复项抛异常 |
| **全有或全无** | 多路由注册要么全部成功要么全部失败 |
| **配置快照隔离** | 进行中的请求永不见操作中途的配置变更——`prepareCall()` 在 harness 层强制执行，适配器须在内部对自身连接事实强制执行 |
| **流式生成** | 适配器实现 `async *stream(options)` 生成器，yield `StreamChunk` |
| **推理内容保留** | 推理内容在每个推理回合上都必须保留——这是跨供应商会话重放和可验证可追溯性的最小可行行为 |

#### llm/stream 瀑布流

每个流式模型调用经过 `llm/stream` 瀑布流：

```typescript
ctx.on('llm/stream', (options, next) => {
  // 预处理：日志记录、指标、请求修改（仅限手工构建）
  return next()  // 委托给适配器流
})
```

瀑布流实现三个横切关注点而不耦合到注册中心或彼此：

| 关注点 | 机制 |
|---|---|
| 请求标记 | `markAgentLoopRequest()` / `isAgentLoopRequest()` — 基于 WeakSet 区分循环请求（只读）与手工构建调用（可转换） |
| 指标收集 | 监听器观察 options 和流结果 |
| 请求拦截 | 手工构建的调用可被转换；循环组装的请求深度冻结 |

`options.provider` 选择适配器，`options.model` 为提供商模型 ID——动态目录适配器可在无需生命周期重配置的情况下提供新模型。

### 六、端到端扩展工作流

工具与适配器遵循相同的注册弧线：

```
1. 声明 inject 依赖
       │
       ▼
2. apply(ctx) 中注册
       │
       ▼
3. 注册表接纳（校验唯一性/模式）
       │
       ▼
4. 提示词组装纳入（工具模式加入 system prompt / 适配器加入路由表）
       │
       ▼
5. 模型调用 → 管线执行 → 结果持久化
       │
       ▼
6. 纤程销毁 → 自动注销 → 从下一次组装中移除
```
