开发一款适合 DSH 的工具，需要同时满足**插件形态契约**、**执行契约**、**表现层契约**和**测试契约**。以下是按优先级整理的完整清单。

---

## 一、插件形态：三件套不可少

每个工具是一个 Cordis 插件，必须导出三个成员：

```ts
export const name = 'my-tool'        // 1. 插件名称
export const inject = ['tools']      // 2. 依赖注入：等待 tools 服务就绪
export function apply(ctx: Context) { // 3. 注册逻辑
  ctx.tools.register(defineTool({ ... }))
}
```

⚠️ **关键：**
- `inject: ['tools']` 使插件等待工具注册表存在
- `ctx.tools.register(...)` 返回的销毁器挂载到插件纤程，卸载时**自动注销**
- 不要在 `apply()` 外部注册——这会绕过生命周期管理

---

## 二、`defineTool` 字段约束

| 字段 | 约束 | 常见错误 |
|------|------|----------|
| `name` | 注册表中必须唯一 | 重复 name 会抛异常 |
| `description` | 面向模型的简明动作描述 | 写成面向人类的长文档会浪费 token |
| `parameters` | 隐式开放对象模式；`defineTool` 编译为 JSON Schema | 使用了 Schema 不支持的类型 |
| `output.schema` | `execute()` 返回值必须通过此 schema 验证 | 返回值与 schema 不匹配 → `isError` |
| `output.render` | 将规范值投影为 `ContentBlock[]` | 在 render 中执行副作用 |
| `timeoutMs` | 正整数，协作式调用截止时间 | 设为 0 或负数 |

---

## 三、`execute()` 七条硬契约（最重要！）

这是工具开发者最容易踩坑的地方，每一条都对应真实的生产缺陷：

### ✅ 规则 1：参数已校验，无需手动校验
`defineTool` 在 `execute` 运行前自动拒绝违反模式的参数（类型、必填键、字面量约束、精确单一联合、嵌套值），抛出带路径的 `ToolArgsError`。**不要重复校验。**

### ✅ 规则 2：注册后定义不可变
注册表持有只读引用。注册后修改模式或替换回调是未定义行为。
```ts
// ❌ 错误
const def = defineTool({ ... })
ctx.tools.register(def)
def.parameters.extra = { ... }  // 篡改已注册定义！
```
热替换的正确姿势：**销毁旧效应 → 重新注册**。

### ✅ 规则 3：执行身份受保护
调用身份（`callId`、`name`、`arguments`、`agent`、`token`）和 `signal` 均为只读。管线在策略启动前冻结参数为分离的无损 JSON。**不要试图篡改 `exec` 对象。**

### ✅ 规则 4：必须返回规范 JSON 值
`execute()` 的返回值会经过：递归遍历物化为分离的无损 JSON → `output.schema` 校验 → `deepFreeze()` → 传给 `output.render`。
```ts
// ❌ 错误：返回不可 JSON 化的值
execute(args, exec) {
  return new Map([['key', 'value']])  // Map 无法无损 JSON 化
}
```

### ✅ 规则 5：区分领域失败与基础设施故障
```ts
// ✅ 正确：领域失败用规范值表示
execute(args, exec) {
  if (!fileExists) return { ok: false, error: 'File not found' }
}

// ❌ 错误：领域失败用 throw 表示
execute(args, exec) {
  if (!fileExists) throw new Error('File not found')  // 这会被记录为 isError
}
```
**基础设施故障**（网络断开、磁盘满）才应该 `throw`。

### ✅ 规则 6：必须遵从 `exec.signal`（强制性！）
```ts
// ✅ 正确：转发 signal
execute(args, exec) {
  return fetch(url, { signal: exec.signal })
}

// ❌ 错误：忽略 signal
execute(args, exec) {
  return fetch(url)  // 用户中止时无法取消！
}
```
注册表通过环绕调度信号替换保留调用者的取消操作——但**你的代码必须配合**。

### ✅ 规则 7：变更类工具必须使用 `presentationMeta`
写/编辑类工具需要投影持久卡片数据（如 diff），核心将投影的 JSON 持久化在 `tool/result` 上并传给 `presentResult`，使重放时差异卡片能携带它们。

来源：[schema.ts](packages/core/tools/src/schema.ts#L480-L570), [index.ts](packages/core/tools/src/index.ts#L200-L260)

## 四、表现层：`presentCall` 与 `presentResult` 的约束

| 函数 | 约束 | 常见错误 |
|------|------|----------|
| `presentCall?(args)` | **纯函数**、无副作用、仅依赖 `args`、重放安全 | 在里面发网络请求或读全局状态 |
| `presentResult?(args, result)` | **纯函数**、无副作用、重放安全 | 在里面修改 DOM 或写文件 |

> **为什么必须纯？** 同一函数在实时流传输和会话日志重放期间都运行。副作用在重放时会重复执行。

**软校验安全网：** `defineTool` 对显示路径做软校验——畸形的已记录参数使包装器返回 `undefined`（通用回退）而非抛异常。**显示绝不能导致重放崩溃。**

## 五、规范值与 render 的职责分离

这是框架中最精妙的分层——**三通道输出**：

| 通道 | 消费者 | 负责人 | 内容 |
|------|--------|--------|------|
| 规范值 | 管线验证 / 快照 / 重渲染 | `output.schema` | 结构化 JSON——程序化 API |
| 面向模型文本 | 模型上下文 | `output.render` | `ContentBlock[]`——人类可读解释 |
| UI 元数据 | 宿主/客户端卡片 | `presentationMeta` + `presentResult` | 差异、路径、围栏块等 |

```ts
// ❌ 错误：把 UI 内容塞进规范值
output: {
  schema: { type: 'string' },  // 规范值里放 diff 文本？
  render: (_args, value) => [{ type: 'text', text: value }],
}

// ✅ 正确：规范值是结构化数据，render 是人类可读文本
output: {
  schema: {
    type: 'object',
    properties: {
      path: { type: 'string' },
      content: { type: 'string' },
    }
  },
  render: (_args, { path, content }) => [
    { type: 'text', text: `Wrote ${content.length} chars to ${path}` }
  ],
}
```

## 六、不要把策略构建到工具本身

**工具只声明它做什么。** 部署策略（超时、重试、审批、沙箱）挂载到管线事件上：

```ts
// ❌ 错误：工具内部硬编码审批逻辑
execute(args, exec) {
  if (isDangerous(args)) {
    if (!userApproved) throw new Error('Need approval')
  }
}

// ✅ 正确：通过 tools/pre-execute 监听器实现
ctx.on('tools/pre-execute', (exec, next) => {
  if (isDangerous(exec)) return { kind: 'ask' }
  return next()
})
```

来源：[adding-a-tool.md](docs/cookbook/adding-a-tool.md#L53-L58)

## 七、中性词汇：不要导入 UI 或传输类型

工具包属于 `dsh-tools` 命名空间——**中性层**：
- ❌ 绝不 `import` React 组件、RPC 类型、CSS 模块
- ✅ 宿主/客户端运行时将每个 `card` 映射为自身的视图组件

这保证了工具可以在 Node.js headless 环境和浏览器环境中同样运行。

## 八、`finalizeContent` 的约束

如果你的工具实现了 `finalizeContent(exec, result)`：

| 约束 | 说明 |
|------|------|
| **同步** | 不能是 async |
| **全量** | 必须处理所有可能的 result 类型 |
| **绝不能抛出异常** | 此阶段在管线末端，异常无法被优雅处理 |

## 十、常见踩坑清单

| 踩坑 | 后果 | 修复 |
|------|------|------|
| `execute` 忽略 `exec.signal` | 用户中止时工具继续运行 | 所有 I/O 操作转发 `signal` |
| 返回不可 JSON 化的值 | 物化失败 → `isError` | 只返回纯 JSON 值 |
| 领域失败用 `throw` | 被管线归类为基础设施故障 | 用规范值表示（`{ ok: false, error }`) |
| 注册后修改定义 | 未定义行为 | 销毁效应后重新注册 |
| `presentCall` 有副作用 | 重放时副作用重复执行 | 保持纯函数 |
| 工具内硬编码策略 | 无法被沙箱/审批覆盖 | 策略挂载到管线事件 |
| 导入 UI 类型 | headless 环境崩溃 | 工具只使用中性词汇 |
| `output.render` 塞入 diff/围栏 | 规范值膨胀、模型 token 浪费 | 用 `presentationMeta` 承载 UI 数据 |
