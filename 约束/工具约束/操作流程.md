工具的安装与卸载本质上是 **Cordis 插件纤程的挂载与拆卸**。整个流程由 Fiber 状态机驱动，每一步都有精确的语义和可验证的不变量。

---

## 一、安装流程：从声明到可用

### 全景时序

```
cordis.yml 声明
      │
      ▼
Loader 读取 YAML → 解析插件条目
      │
      ▼
ctx.plugin(myTool)  →  创建 Fiber (PENDING)
      │
      ▼
检查 inject: ['tools'] 依赖是否可用
      │
      ├── 否 → 停留在 PENDING（静默等待，不崩溃）
      │
      └── 是 → 转入 LOADING
                │
                ▼
              调用 apply(ctx)
                │
                ├── apply 内执行 ctx.tools.register(defineTool({...}))
                │     │
                │     ├── defineTool 编译 parameters → JSON Schema
                │     ├── 返回值类型推导（args.path: string 等）
                │     └── register() 将清理函数挂载到 fiber 副作用列表
                │
                ▼
              apply() 正常返回 → 转入 ACTIVE
                │
                ├── 工具模式加入系统提示词组装
                ├── 工具可被模型调用
                └── emit tools/change 事件通知所有观察者
```

### 各阶段详解

| 阶段 | 触发条件 | 可注册副作用？ | 工具状态 |
|------|----------|----------------|----------|
| **PENDING** | `ctx.plugin()` 被调用 | 否 | 不可用，静默等待 |
| **LOADING** | 所有 `inject` 依赖可用 | 是 | `apply()` 执行中，注册进行中 |
| **ACTIVE** | `apply()` 正常返回 | 是 | 已注册，模式加入提示词，可被调用 |
| **FAILED** | `apply()` 或配置校验抛异常 | 否 | 从未注册，不影响其他插件 |

> **PENDING 是合法状态。** 如果 `tools` 服务尚未就绪，工具插件会安静等待，不崩溃、不部分运行。这是 Cordis 的核心设计：**声明优于顺序**。

### 安装的代码形态

```ts
// 1. 插件声明三件套
export const name = 'my-tool'
export const inject = ['tools']        // 等待 tools 服务
export function apply(ctx: Context) {
  // 2. 注册工具（副作用）
  ctx.tools.register(defineTool({
    name: 'read_file',
    description: 'Read a file from disk.',
    parameters: {
      path: { type: 'string', required: true },
    },
    output: {
      schema: { type: 'string' },
      render: (_args, value) => [{ type: 'text', text: value }],
    },
    async execute(args, exec) {
      return readFile(args.path, { encoding: 'utf8', signal: exec.signal })
    },
  }))
  // register() 返回的销毁器已自动挂载到 fiber——无需手动管理
}
```

### 安装的 YAML 形态

```yaml
# cordis.yml
- id: my-tool
  name: './my-tool.ts'    # 本地模块路径
  # 或 name: '@my-org/dsh-tool-my-tool'  # npm 包
```

启动时：Launcher 创建根 `Context` → 挂载 Loader → Loader 读取 YAML → 解析每个条目 → `ctx.plugin()` 挂载。

## 二、卸载流程：从 ACTIVE 到 DISPOSED

### 触发卸载的四种路径

| 触发方式 | 场景 |
|----------|------|
| **显式销毁** `fiber.dispose()` | 编程式卸载 |
| **父纤程卸载** | 父插件的 fiber dispose 递归级联子插件 |
| **服务丢失** | `inject` 声明的某个服务其提供者被卸载/热替换 |
| **配置重载/HMR** | `cordis-plugin-hmr` 检测到文件变更 → 卸载 → 重新加载 |

### 卸载时序

```
触发卸载
    │
    ▼
Fiber 转入 UNLOADING
    │
    ▼
按注册的逆序执行清理函数（副作用逆转）
    │
    ├── ctx.tools.register() 的清理 → 从注册表移除工具
    │     │
    │     ├── 工具模式从下一次系统提示词组装中移除
    │     ├── 工具不再可被模型调用
    │     └── emit tools/change 事件通知所有观察者
    │
    ├── ctx.on() 的清理 → 从事件总线移除监听器
    ├── ctx.provide() 的清理 → 移除服务实现
    ├── ctx.plugin(child) 的清理 → 递归销毁子 fiber
    └── ctx.effect() 的清理 → 执行自定义清理函数
    │
    ▼
所有清理完成 → Fiber 转入 DISPOSED
    │
    ├── fiber.uid 变为 null
    └── fiber 永久移除，不可重启
```

### Cordis 自动代管的副作用逆转

你**不需要**手动写注销代码。以下 API 的清理全部由框架自动执行：

| API | 卸载时自动清理 |
|-----|----------------|
| `ctx.tools.register(...)` | 从注册表移除工具模式 |
| `ctx.on(event, listener)` | 从事件总线移除监听器 |
| `ctx.plugin(child)` | 子 fiber 随父 fiber 一同销毁 |
| `ctx.provide(name, impl)` | 移除服务实现 |
| `ctx.effect(disposer)` | 调用你返回的清理函数 |

## 三、重新激活：UNLOADING → LOADING

这是 HMR 和服务热替换的核心路径：

```
服务提供者被替换（如 shell 从 local → remote）
    │
    ▼
依赖 'shell' 的工具插件 fiber 被卸载（UNLOADING）
    │
    ▼
清理完成，但 fiber 未 DISPOSED
    │
    ▼
新提供者就绪 → fiber 直接转回 LOADING
    │
    ▼
重新执行 apply(ctx)（针对新实现）
    │
    ▼
转回 ACTIVE
```

> **关键洞见：`inject` 并非一次性的启动检查。** 它是持续性的依赖约束——当服务在运行时消失或替换，所有依赖该服务的纤程都会级联卸载并在服务返回时重新加载。

## 四、完整状态机

```
                    ┌──────────────────────────────────┐
                    │  ctx.plugin() 被调用              │
                    └──────────┬───────────────────────┘
                               ▼
                          ┌─────────┐
                 ┌─────── │ PENDING │ ───────┐
                 │        └────┬────┘         │
                 │             │ 依赖可用      │ 显式 dispose / 父卸载
                 │             ▼              │
                 │        ┌─────────┐         │
     依赖重获    │        │ LOADING │         │
     ┌──────────┤        └────┬────┘         │
     │          │             │               │
     │          │     ┌───────┴───────┐       │
     │          │     │               │       │
     │          │  apply()成功    apply()抛异常│
     │          │     │               │       │
     │          │     ▼               ▼       │
     │          │ ┌─────────┐   ┌─────────┐  │
     │          │ │ ACTIVE  │   │ FAILED  │──┘
     │          │ └────┬────┘   └────┬────┘
     │          │      │               │
     │          │  dispose/           │ dispose
     │          │  服务丢失/重载      │
     │          │      │               │
     │          │      ▼               ▼
     │          │ ┌─────────────┐
     │          └─│  UNLOADING  │
     │            └──────┬──────┘
     │                   │ 所有清理器完成
     │                   ▼
     │            ┌───────────┐
     └────────────│ DISPOSED  │  (终态，不可重启)
                  └───────────┘
```

## 五、操作 API 一览

| 操作 | API | 语义 |
|------|-----|------|
| 编程式挂载 | `ctx.plugin(myTool)` | 创建 fiber，返回 `Fiber & PromiseLike<Fiber>` |
| 等待加载完成 | `await fiber` / `fiber.await()` | 解决至 ACTIVE 或 FAILED |
| 销毁 | `await fiber.dispose()` | 卸载 + 等待所有清理完成（含子纤程递归） |
| 热重载 | `fiber.reload()` | 销毁 + 用当前配置重新加载 |
| 配置变更重载 | `fiber.update(newConfig)` | 校验新配置 → 重启 |
| 查询状态 | `fiber.state` | 当前 FiberState 枚举 |
| 查询副作用 | `fiber.getEffects()` | 已注册副作用的元数据树 |

## 六、常见陷阱

| 陷阱 | 后果 | 正解 |
|------|------|------|
| 在 `apply()` 外注册工具 | 绕过生命周期，卸载时泄漏 | 所有注册在 `apply()` 内 |
| 手动维护 `removeEventListener` | 遗漏清理，卸载后监听器仍在运行 | 用 `ctx.on()`，框架自动管理 |
| `apply()` 抛异常后期望部分运行 | 进入 FAILED，**零副作用存活** | `apply()` 要么全成功，要么全失败 |
| 在 DISPOSED 状态调 `ctx.effect()` | 抛 `CordisError('INACTIVE_EFFECT')` | 检查 `fiber.state` 再操作 |
| 多个异步清理函数依赖顺序 | 并发执行，顺序不确定 | 有序清理放在同一个清理函数中依次 await |
