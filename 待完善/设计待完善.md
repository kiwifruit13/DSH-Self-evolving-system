### P0-19 split() 完全绕过重叠校验

**问题**：`split()` 创建子节点时不执行任何重叠校验。`OfflinePlanner` 的 Phase 2（`_phase_validate`）只在从反馈举证创建全新节点时调用 `OverlapChecker.check()`，但 `split()` 是另一条创建路径，它完全绕过了这个门禁。

**代码证据**：
```python
def split(self, parent_category_id, child_name, reason, ...):
    ...
    child_category_id = f"{parent_category_id}.{child_name}"
    existing = self._storage.get_routing_entry(child_category_id)
    if existing is not None:
        raise ValueError(f"子节点 '{child_category_id}' 已存在")
    # 只检查了"完全同名"，没有检查"语义重叠"
```

**后果**：
- 分裂路径和举证路径使用两套规则：举证路径有重叠门禁，分裂路径完全没有
- 子代理可以无限分裂出语义重复的节点，路由表膨胀不受控制
- 重叠校验器的整个设计被 `split()` 这一条旁路完全架空

**典型场景**：
```
已有节点: network.timeout.connect
已有节点: network.timeout.read

子代理执行 split("network.timeout", "socket") → 创建 network.timeout.socket
  ↓ 没有校验 socket 是否已经语义覆盖在 connect 之下
  ↓ 如果 connect 的边界是"处理所有连接超时"，那 socket 是冗余的
```

**修复方向**：
```
方案 A：split() 内部调用 OverlapChecker.check()
- 用 child_name 构造候选 category_id 和 boundary
- 检查与所有现有节点（含同级兄弟节点）的重叠
- 重叠率 > 阈值时拒绝分裂，返回建议

方案 B：新增 validate_split() 方法
- 作为 split() 的前置调用
- 检查兄弟节点重叠 + 与已有子节点的包含关系
- split() 在 validate_split() 通过后才会创建

方案 C：统一入口
- 将 OfflinePlanner 的"新建"和 split 的"分裂"统一到同一个 create_node() 方法
- 统一的重叠校验逻辑
```

### P0-20 insert() 和 update() 语义完全相同（都是 upsert）

**问题**：`insert()` 和 `update()` 都直接调用 `self._storage.upsert_routing_entry(entry)`，两者没有任何区别。

**代码证据**：
```python
def insert(self, entry):
    self._storage.upsert_routing_entry(entry)
    return entry

def update(self, entry):
    self._storage.upsert_routing_entry(entry)
    return entry
#            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 完全相同
```

**后果**：
- `insert()` 静默覆盖已存在的条目——这不是"插入"，是"替换"
- 调用方无法区分"新增"和"更新"两种语义
- 如果 `insert()` 本意是"不存在则插入，存在则报错"，那当前实现完全违背了数据完整性约束
- 如果 `insert()` 本意就是 upsert，那 `update()` 就是冗余方法，二者应该合并

**典型场景**：
```
entry1 = RoutingTableEntry(category_id="network.http_429", stats={"freq": 100, ...})
rt.insert(entry1)  # 第一次调用：正常插入

# 后续
entry2 = RoutingTableEntry(category_id="network.http_429", stats={"freq": 5, ...})
rt.insert(entry2)  # 第二次调用：静默覆盖了 freq=100 → freq=5
# 调用方完全不知道发生了覆盖
```

**修复方向**：
```
方案 A：insert() 改为真正的 INSERT（存在则报错）
- insert() 先 get() 检查，存在则 raise ValueError
- update() 继续用 upsert
- 符合 SQL 的 INSERT/UPDATE 语义

方案 B：insert() = update()，合并方法
- 删除 insert()，只保留 update()
- 或者重命名 update() 为 upsert()
- 在文档中明确这是 upsert 语义

方案 C：insert() 返回覆盖标识
- 修改 Storage.upsert_routing_entry 返回是否覆盖
- rt.insert() 返回 (entry, was_replaced: bool)
- 调用方可据此判断是否发生了静默覆盖
```

### P0-21 分裂后子节点继承父节点完整 stats

**问题**：`split()` 中 `child_entry = RoutingTableEntry(..., stats=parent.stats.copy(), ...)`。子节点刚被创建就继承了父节点的完整统计值（freq=200, impact=0.95, trend=0.1, recover_cost=1）。

**代码证据**：
```python
child_entry = RoutingTableEntry(
    category_id=child_category_id,
    stats=parent.stats.copy(),  # ← 问题在这里
    local_map=child_lm,
    tags=child_tags,
)
```

**后果**：
- 分裂前：`network.timeout` 得分 = f(freq=200, impact=0.95, ...)
- 分裂后：`network.timeout.connect` 得分 = f(freq=200, impact=0.95, ...)
- 父子节点得分**完全相同**——路由表的树状结构在排序维度上毫无意义
- 随着分裂持续进行，路由表中会积累大量"得分相同但语义不同"的冗余节点

**修复方向**：
```
方案 A：子节点 stats 初始化为零
- stats = {"freq": 0, "impact": 0, "trend": 0, "recover_cost": 0}
- 子节点从零开始积累统计

方案 B：子节点 stats 继承部分 + 缩放
- freq 继承但标记为"继承值"，需要独立积累
- impact 不继承（子节点还未验证修复效果）
- 设置一个标志位 inherited_stats=True，等独立运行后清除

方案 C：子节点初始 stats 用父节点中位值
- freq = parent.freq / 2
- impact = parent.impact / 2
- 让子节点从"半初始状态"开始积累
```

### P0-22 prune() 是空壳——只标记不合并

**问题**：`prune_lowest()` 只往 `maintenance_log` 里打一个 `prune_pending` 标记，然后返回 category_id 列表就什么都不做了。被标记的节点还在路由表里参与排序、消耗 Skill 编译资源。

**代码证据**：
```python
def prune_lowest(self, threshold=0.1, bottom_pct=0.1, ...):
    ...
    candidates = [s.category_id for s in bottom_scores if s.final_score <= threshold]

    for cat_id in candidates:
        entry = self._storage.get_routing_entry(cat_id)
        if entry is not None:
            entry.local_map.append_log("prune_pending", reason, actor)
            self._storage.upsert_routing_entry(entry)

    return candidates  # 只返回列表，不做任何合并/删除操作
```

**后果**：
- 节点还在路由表里，还在参与排序，还在消耗子代理的 Skill 编译资源
- 这个方法执行了 N 次，路由表里的低分节点依然存在——"写了但等于没写"的方法
- 如果调用方认为调用 `prune_lowest()` 就是完成了剪枝，那路由表永远不会被真正修剪

**修复方向**：
```
方案 A：prune() 内部执行实际合并
- 将待剪枝节点合并到其父节点
- 合并规则：被合并节点的 stats 加到父节点，tags 取并集，
  maintenance_log 追加 "merged_from" 记录
- 被合并节点标记为 deleted（软删除）或硬删除

方案 B：prune() 返回合并计划，由调用方确认执行
- 返回 MergePlan 对象，包含待合并对和合并策略
- 子代理确认执行后调用 merge() 方法实际执行

方案 C：增加 merge() 方法
- prune() 继续只识别，merge() 负责执行合并
- 调用方：prune() → review candidates → merge()
```

### P1-23 rank() 默认 `days_since_last_seen=0`，时间衰减形同虚设

**问题**：`rank()` 方法的 `days_since_last_seen` 默认值为 `0.0`，衰减因子恒为 `1.0`，时间维度完全没有参与计算。

**代码证据**：
```python
def rank(self, days_since_last_seen: float = 0.0, ...):
    entries = self.query(root_category=root_category)
    return self._scorer.rank(entries, days_since_last_seen=days_since_last_seen)
```

**后果**：
- `scoring.py` 中精心设计的时间衰减曲线（半衰期 7 天）在当前调用路径下完全不起作用
- `top_k()` 也使用了同样的默认值，整个排序系统的时间维度被绕过

**根本原因**：
- `days_since_last_seen` 需要每个节点的**独立时间戳**，但当前 stats 结构中没有存储时间戳
- 只能统一传一个值，对所有节点来说是同一个衰减因子——不是数据驱动的

**修复方向**：
```
方案 A：stats 增加 last_seen 字段
- stats = {..., "last_seen": "2026-08-27T04:00:00Z"}
- rank() 内部为每个节点计算独立的 days_since_last_seen

方案 B：rank() 默认计算
- rank() 内部用当前时间减去每个节点的 last_seen
- 无需外部传入，默认值不再为 0

方案 C：移除时间衰减，承认当前无数据
- 要么接入时间戳，要么暂时移除衰减维度
```

### P1-24 split() 无树深度限制

**问题**：`split()` 没有深度限制，可以无限分裂：`network.timeout` → `network.timeout.connect` → `network.timeout.connect.socket` → ...

**后果**：
- 路由表可能膨胀为极深的树，category_id 越来越长
- 深层次的节点在排序中得分极低，永远不会被选中
- 主代理精确查询时需要输入极长的 category_id

**修复方向**：
```
方案 A：硬深度限制
- MAX_DEPTH = 3
- split() 检查 len(parent_category_id.split('.')) + 1 > MAX_DEPTH 时拒绝

方案 B：软深度建议
- 超过建议深度时增加日志警告，由子代理决定是否继续

方案 C：按 stats 衰减限制
- 深度越深，初始 stats 衰减越严重
- 深层节点自然得分低，靠排序机制自然淘汰
```

### P1-25 query_by_expression() 排序依赖外部 map，脆弱

**问题**：`query_by_expression()` 用 `ranked_map.get(e.category_id, 0.0)` 排序，防御性不足。

**代码证据**：
```python
ranked = self._scorer.rank(candidates, days_since_last_seen=0)
ranked_map = {r.category_id: r.final_score for r in ranked}
matched.sort(key=lambda e: ranked_map.get(e.category_id, 0.0), reverse=True)
```

**后果**：
- `matched` 理论上 ⊆ `candidates`，但如果 `evaluate_query` 和 `_scorer.rank` 范围有差异，条目会静默得 0.0 分
- `days_since_last_seen=0` 硬编码在此处，进一步削弱了时间衰减

**修复方向**：
```
方案 A：显式校验，对不在 ranked_map 中的条目打印警告日志

方案 B：在 matched 列表上重新计算得分，不依赖外部 ranked_map

方案 C：保持现状，添加注释说明依赖关系
```

### P1-26 split() 不校验子节点与已有同级节点的重叠

**问题**：`split()` 只检查 `child_category_id` 是否已存在（精确匹配），不检查新子节点是否与已有同级兄弟节点在语义上重叠。

**后果**：
- 已有 `network.timeout.read`（边界："仅处理读超时"）
- 已有 `network.timeout.connect`（边界："仅处理连接超时"）
- 执行 `split("network.timeout", "tcp")` → 创建 `network.timeout.tcp`（边界继承自父节点"处理所有超时"）
- `tcp` 同时覆盖了 `read` 和 `connect`，但它被允许创建了

**修复方向**：
```
方案 A：split() 内部对同级节点做重叠检测
- 获取所有同级兄弟节点
- 对每个兄弟计算与候选 child_name 的重叠率
- 最高重叠率 > 阈值时拒绝分裂

方案 B：新增 validate_new_child() 方法
- 专门检查候选子节点与同级兄弟的重叠
```

### P2-29 split() 后父节点 stats 未重新分配

**问题**：分裂后，父节点的 stats 保持不变。但父节点现在包含了子节点的部分场景，它的 stats 应该反映"除了子节点之外的剩余场景"。

**后果**：
- 分裂前：`network.timeout` freq=200（覆盖所有超时场景）
- 分裂后：`network.timeout` freq=200，`network.timeout.connect` freq=200（继承）
- 两者 stats 完全相同——路由表统计被重复计算

**修复方向**：
```
方案 A：分裂时按比例分配 stats，父节点减少，子节点获得减少量，保持总量不变

方案 B：标记父子关系后由子代理定期重算
```

### P0-1 趋势维度无数据源

**问题**：`trend` 维度从 `stats["trend"]` 读取，但整个代码库中 `trend` 从未被计算，只在子代理蒸馏时硬编码为 `0.0`。

**现状**：
- `normalize_trend(0.0)` 返回 `0.5`（`(0+1)/2=0.5`）
- 每个节点的 trend 归一化得分恒为 `0.5`
- 趋势维度恒贡献 `0.5 × 0.20 = 0.10` 分给所有节点
- 这是一个**常量偏移量**，不是真实趋势信息

**后果**：
- 20% 的权重分配给一个无效维度
- 排序结果实际上只是三维权重（`freq 25% + impact 35% + cost 20%`）加上一个固定偏移
- 趋势维度名存实亡

**修复方向**：
```
方案 A：接入真实趋势计算
- 记录每个节点的"最近 N 次出现时间序列"
- 用滑动窗口差值计算：trend = (最近7天频次 - 前7天频次) / 前7天频次
- 钳制到 [-1, 1]

方案 B：移除 trend 维度，把 20% 权重重新分配给其他维度
- 重新校准 freq/impact/cost 的权重比例

方案 C：保留字段但标记为 DEPRECATED，直到数据管道接入
```

### P0-2 权重无反馈回路（开环系统）

**问题**：`freq=0.25, impact=0.35, trend=0.20, cost=0.20` 是写死的，没有机制根据排序结果的实际执行效果来调整权重。

**后果**：
- 系统永远无法学习"在当前场景下哪个维度更重要"
- 如果 Top 1 节点被执行后修复失败率很高，排序权重不会调整
- 冷启动期（数据稀疏）用稳定期（数据充足）的权重，必然不合理

**修复方向**：
```
方案 A：固定周期重校准
- 每运行 N 次 Skill 执行，收集 {排序得分, 执行结果(成功/失败), 实际代价} 三元组
- 用简单的线性回归或梯度下降更新权重
- 权重更新公式：w_i = w_i + lr * Σ(error * x_i) / N
- 其中 error = (实际修复结果 - 排序得分预测的修复概率)

方案 B：分层权重（按根分类）
- 为每个根分类（network / data_parsing / llm_inference / ...）维护独立的权重向量
- 初始化为全局默认值，随数据积累独立演化
- 好处：network 类错误趋势权重高，llm_inference 类错误 impact 权重高，自动适应

方案 C：贝叶斯优化权重
- 权重视为高斯分布的均值和方差
- 每次执行结果作为观测，更新后验分布
- 排序时使用后验均值，方差作为置信度
```

### P1-3 归一化参数拍脑袋

**问题**：`freq_max=1000`, `cost_max=10` 没有数据依据，是写死的全局参数。

**后果**：
- 线性归一在幂律/长尾分布下表现差（真实错误频次分布大概率是幂律的）
- 高频错误（5000次）和中等频率错误（500次）的归一化得分差只有 0.5（因为被钳制到 1.0）
- `cost_max=10` 意味着超过 10 次/分钟的恢复代价在得分上几乎没有区分度

**修复方向**：
```
方案 A：数据驱动归一化
- 初始化时扫描所有路由表节点的 freq 分布
- 用 P95 分位数作为 freq_max（而非固定 1000）
- cost_max 同理，取 P95 分位数

方案 B：自适应归一化
- 每新增 N 个节点后重新计算分位数
- freq_max 随系统运行动态增长

方案 C：对数归一化（适用于幂律分布）
- freq_norm = log(freq + 1) / log(freq_max + 1)
- 在长尾分布下更好地区分低频次节点
```

### P1-4 时间衰减一刀切

**问题**：`half_life=7` 天全局共享，所有节点（无论频次高低）使用同一个衰减曲线。

**后果**：
- 出现 500 次的系统性错误和出现 3 次的偶发错误，衰减速度相同
- 高频错误应该衰减更慢（更可能是系统性问题，需要持续关注）
- 低频错误应该衰减更快（更可能是噪声）
- 衰减最终归零，但有些慢速 bug 需要持续关注

**修复方向**：
```
方案 A：频次自适应衰减
- half_life = base_half_life * (freq / median_freq) 的某种函数
- 高频节点衰减慢，低频节点衰减快

方案 B：对数衰减（永不归零）
- decay = 1 / (1 + days_since_last_seen / half_life)
- 而非指数衰减 2^(-days/half_life)
- 好处：不会把长期未出现的错误彻底遗忘

方案 C：分类型衰减
- network 类错误：half_life = 14 天（网络问题通常是系统性的）
- llm_inference 类错误：half_life = 3 天（LLM 问题可能随模型更新自愈）
- data_parsing 类错误：half_life = 7 天
```

### P2-5 四维相关性导致双重计数

**问题**：freq 和 trend 天然正相关；impact 和 cost 可能负相关。独立加权会把相关性隐含地放大。

**后果**：
- 一个"高频 + 趋势上升"的错误，它的 freq 权重和 trend 权重各贡献一次，等于这个信号被算了两次
- 权重总和虽然是 100%，但实际的有效独立维度不足 4 个

**修复方向**：
```
方案 A：主成分分析（PCA）
- 对四维归一化后的特征向量做 PCA
- 用前 2-3 个主成分替代原始四维，消除相关性
- 缺点：可解释性下降（主成分不是 freq/impact/trend/cost）

方案 B：去相关权重
- 先计算四维的相关矩阵
- 用 `Σ^{-1} * w` 替代原始权重 w（类似马氏距离）
- 保留原始维度的可解释性

方案 C：接受相关性，明确标注
- 在文档中明确说明 freq 和 trend 是相关维度
- 权重设计时已经考虑到这一点（freq 25% + trend 20% 实际是"频次相关"维度的 45%）
- 无需修改代码，只修改文档
```

### P2-6 无数据量感知（稀疏灾难）

**问题**：`freq=1` 的节点和 `freq=100` 的节点，归一化得分只差 0.099，没有区分"统计显著"和"噪声"。

**后果**：
- 一次性噪声错误被当作真实模式参与排序
- 冷启动期的少量错误被高估

**修复方向**：
```
方案 A：贝叶斯先验平滑
- 给每个维度的真实值加一个拉普拉斯平滑：
  freq_smoothed = (freq + α) / (total_obs + α * K)
- α 是平滑系数，K 是可能的频次值数

方案 B：最小频次阈值
- freq < min_freq（如 3）的节点不参与排序，标记为"待观察"
- 只进入待观察队列，不在主排序中竞争

方案 C：频次置信度衰减
- 引入置信度系数 c = min(1.0, freq / min_freq_for_confidence)
- final_score = priority × decay × c
```

### P3-7 排序结果为标量，主代理缺乏决策灵活性

**问题**：四维被压成一个标量 `final_score`，主代理只能按标量排序"执行 Top 1"，无法根据当前系统状态做差异化选择。

**后果**：
- 系统负载高时，主代理应该优先"低代价"方案，但排序系统只给一个数字
- 用户等待时，主代理应该优先"高影响"方案
- 主代理被迫在"最优排序"和"当前需求"之间二选一

**修复方向**：
```
方案 A：多目标排序
- rank() 返回每个维度的得分 + 综合得分
- 主代理可以根据当前上下文选择排序维度：
  rank_by=cost      → 当前负载高，优先低代价
  rank_by=impact    → 用户等待，优先高影响
  rank_by=overall   → 默认综合排序

方案 B：Pareto 前沿
- 不压缩为标量，返回 Pareto 最优解集
- 主代理从 Pareto 前沿中选择一个符合当前约束的解
```

### P3-8 无置信度度量

**问题**：`final_score=0.7321` 看起来精确，但没有不确定性信息。`freq=3` 和 `freq=300` 的节点，得分可能只差 0.3，但可信度差 100 倍。

**后果**：
- 主代理无法判断"我对这个排序有多自信"
- 无法做基于置信度的降级策略（如"置信度 < 0.7 时回退到通用兜底策略"）

**修复方向**：
```
方案 A：得分方差
- 每个维度的归一化得分附带方差（从原始数据分布计算）
- 综合得分 = 均值，置信度 = 1 / (综合标准差 + ε)
- 排序时返回 (score, confidence) 二元组

方案 B：Bootstrap 置信区间
- 对排序结果做 Bootstrap 采样
- 返回得分的 95% 置信区间 [low, high]
- 置信区间越窄，越可信
```

### P0-9 candidate_signature 参数未使用

**问题**：`check(candidate_category_id, candidate_signature, candidate_boundary)` 方法接收了 `candidate_signature` 参数，但实际计算签名相似度时用的是 `candidate_category_id` 而非 `candidate_signature`。

**代码证据**：
```python
def check(self, candidate_category_id, candidate_signature, candidate_boundary):
    ...
    sig_sim = _signature_similarity(candidate_category_id, entry.category_id)
    #                              ^^^^^^^^^^^^^^^^^^^^^^
    # 应该用 candidate_signature 吗？
```

**后果**：
- `candidate_signature` 参数形同虚设，调用方传什么值都不影响结果
- 签名相似度实际比较的是两个 category_id 的字符串距离（如 `"data_parsing.graphql__field__user__not_found"` vs `"data_parsing.graphql_field_user_not_found"`）
- 两个 category_id 的 Levenshtein 距离受下划线数量、命名规范影响极大，不代表错误签名的真实相似度

**修复方向**：
```
方案 A：用 candidate_signature 替代 candidate_category_id 做签名相似度计算
- _signature_similarity(candidate_signature, entry.category_id.split('.')[1:])
- 好处：比较的是错误签名的语义相似度，而非命名规范

方案 B：两个维度都保留
- sig_sim = _signature_similarity(candidate_signature, entry_signature)
- 但 entry_signature 未存储，需要从 boundary 或 error_stack 提取
- 需要修改存储层，增加 signature 字段

方案 C：明确语义，重命名
- 将 candidate_signature 字段从 check() 方法中移除
- 将内部逻辑改为基于 category_id 的相似度，并更新函数文档
```

### P0-10 根分类权重的二元陷阱

**问题**：`root_match` 是 0 或 1 的二元值，权重 0.3。这意味着**不同根分类之间的最大可能重叠率被硬上限锁死在 0.7**。

**数学推导**：
```
不同根分类：max_overlap = 0.4×sig_max + 0.3×0.0 + 0.3×bound_max = 0.7
同根分类：  max_overlap = 0.4×sig_max + 0.3×1.0 + 0.3×bound_max = 1.0
```

**后果**：
- 不同根分类的错误**永远被拒绝**（0.7 不 < 0.7 阈值）
- 即使一个 network 类的错误和一个 llm_inference 类的错误在语义上完全无关，只要 category_id 和 boundary 碰巧相似（如都是 "timeout"），重叠率也会达到 0.7 被拒绝
- 相反，同根分类下两个语义完全不同但 boundary 高度相似的错误，可能因为 root_match=1.0 直接越过阈值

**这导致了一种荒谬场景**：
```
network.http_429  vs  network.http_500          → 0.4×0.57 + 0.3×1.0 + 0.3×~1.0 ≈ 0.86 → 拒绝 ❌
network.http_429  vs  llm_inference.timeout     → 0.4×0.0  + 0.3×0.0 + 0.3×0.2   ≈ 0.06 → 允许 ✅
```

两个 http 错误（明显属于同一大类，应合并处理）被拒绝，而一个 http 错误和一个 LLM 错误（完全不同领域）被允许。这与设计初衷**完全相反**。

**修复方向**：
```
方案 A：根分类作为硬性过滤而非加权维度
- 先按根分类分组，只在同根分类内部计算重叠率
- 不同根分类默认不重叠（直接允许创建）
- 好处：语义正确，不同领域不应互相阻挡

方案 B：根分类改为模糊匹配
- root_match 不是 0/1，而是基于分类距离的连续值
- 如 network → data_parsing 的距离小于 network → llm_inference
- 需要定义根分类之间的距离矩阵

方案 C：移除根分类维度，只保留签名+边界
- 根分类匹配天然包含在 category_id 相似度中
- 去掉 0.3 的 root 权重，重新分配给 sig/bound
- 简化公式：total = 0.5 * sig_sim + 0.5 * bound_overlap
```

### P0-11 Jaccard 边界重叠度对短语长度极度敏感

**问题**：`_boundary_overlap` 使用词级 Jaccard 系数 `|交集|/|并集|`。Jaccard 在长短不同的短语之间表现极其不稳定。

**典型场景**：
```
短语 A: "仅处理 HTTP 429 限流"
短语 B: "仅处理 HTTP 429 限流，不处理 TCP 超时"

交集 = {"仅", "处理", "HTTP", "429", "限流"} = 5
并集 = {"仅", "处理", "HTTP", "429", "限流", "不", "TCP", "超时"} = 8
Jaccard = 5/8 = 0.625
```

这两个短语语义高度相关（一个是另一个的子集），但 Jaccard 只给出 0.625，远低于 0.7 阈值。这意味着它们被认为是"足够不同"——可以被同时创建。

而反过来：
```
短语 A: "仅处理 HTTP 429"
短语 B: "仅处理 HTTP 429"

Jaccard = 1.0 → 拒绝
```

**后果**：
- **子集关系无法识别**：长边界包含短边界时，Jaccard 偏低，系统错误地允许创建"子集节点"
- **短语长度差异导致误判**：一个节点写 5 个词，另一个写 20 个词，即使语义相同 Jaccard 也很低
- **短词权重过高**：Jaccard 不区分"仅""处理"等停用词和"HTTP""429"等语义关键词，"仅处理"两个词的出现会显著提高 Jaccard 而不提供实际信息

**修复方向**：
```
方案 A：包含关系检测
- 额外检测 words1.issubset(words2) 或 words2.issubset(words1)
- 如果是子集关系，直接标记为高重叠（如 0.9）
- 无需 Jaccard，子集关系本身就是强重叠信号

方案 B：停用词过滤 + TF-IDF 加权
- 移除"仅""处理""不""进行""相关"等停用词
- 剩余词汇用 TF-IDF 加权，语义关键词权重更高
- Jaccard 改为基于加权版本的 Dice 系数

方案 C：SequenceMatcher（Python 标准库）
- from difflib import SequenceMatcher
- ratio = SequenceMatcher(None, boundary1, boundary2).ratio()
- 天然处理包含关系和长度差异
```

### P1-12 无子集关系检测

**问题**：重叠校验只检测"相似度"，不检测"包含关系"。当一个新错误的 boundary_rules 是已有节点的子集时（如"仅处理 HTTP 429" 是 "仅处理 HTTP 429 限流"的子集），当前设计无法识别。

**后果**：
- 路由表中会积累大量"语义包含"的重复节点
- 节点 A: "仅处理 HTTP 429"
- 节点 B: "仅处理 HTTP 429 限流"
- 两者 Jaccard = 0.625 < 0.7，同时存在
- 但实际上 B 完全覆盖了 A 的场景，A 是冗余的

**修复方向**：
```
方案 A：子集优先检测
- 在 Jaccard 之前先检测 words1 ⊆ words2 或 words2 ⊆ words1
- 如果是子集关系，重叠率直接设为 max(len(子集)/len(全集), Jaccard)

方案 B：反向匹配
- 对已有节点集合做包含检测
- 对新节点的每个边界关键词，检查是否被已有节点覆盖
```

### P1-13 O(n) 全量扫描无索引

**问题**：`check()` 方法每次都对路由表做全量扫描，逐条计算 Levenshtein 距离（O(m×n)）。路由表有 100 个节点时每次校验是 100 次 O(m×n) 计算。

**后果**：
- 路由表 100 节点 → 100 次 Levenshtein，每次约 20×30 = 600 次操作
- 路由表 1000 节点 → 1000 次 Levenshtein，约 6000 次操作
- 如果子代理每批消费 10 个举证包，就是 10×1000 = 10000 次 Levenshtein
- 路由表增长后校验成本线性增长，没有上界

**修复方向**：
```
方案 A：前缀树（Trie）索引
- 按 category_id 的根分类建立 Trie
- 只在同根分类的子树内做全量扫描
- 将 O(n) 降为 O(n_root)

方案 B：预计算签名指纹
- 对每个已有节点预计算 error_signature 的 hash 或编辑距离上限
- 先用上限做过滤，只对可能相似的节点做精确计算

方案 C：接受 O(n) 复杂度
- 路由表节点数通常在几十到几百之间，O(n) 在实际范围内可接受
- 如果路由表超过 1000 节点才考虑优化
```

### P1-14 阈值 0.7 是魔法数字

**问题**：`threshold = 0.7` 写死在 `OverlapChecker.__init__` 中，没有数据依据，没有自适应机制。

**后果**：
- 0.7 是基于直觉的猜测，未经实际数据验证
- 不同根分类可能需要不同的阈值：
  - `network` 类错误差异度大，0.7 可能太宽松
  - `data_parsing` 类错误差异度小，0.7 可能太严格
- 阈值不会随系统运行而调整

**修复方向**：
```
方案 A：分根分类阈值
- 每个根分类有独立的 threshold
- network: 0.6（差异度大，更严格）
- data_parsing: 0.8（差异度小，更宽松）

方案 B：自适应阈值
- 初始值 0.7
- 每 N 次拒绝后，统计被拒绝节点的 category_id 差异
- 如果大量合理的错误被误拒，调高阈值

方案 C：保留硬编码，添加注释
- 如果路由表规模小，0.7 够用
- 添加注释说明调参方法，等系统运行足够长时间后再优化
```

### P2-15 边界提取的字符切分问题

**问题**：`boundary_rules.split()` 默认按空白字符切分。但中文文本没有空格分词，`"仅处理 HTTP 429 限流"` 会被切分为 `["仅处理", "HTTP", "429", "限流"]`。"仅处理"是一个词，但它本身没有语义（停用词），却占了并集的一份。

**后果**：
- 中文停用词（仅、处理、不、进行、相关）对 Jaccard 贡献了无意义的交集
- 语义关键词（HTTP、429、限流、SSL、证书）和停用词权重相同
- 中英文混合文本的分词不一致（中文按字面切分，英文按空格切分）

**修复方向**：
```
方案 A：简单停用词表过滤
- STOP_WORDS = {"仅", "处理", "不", "进行", "相关", "类", "已", "尝试"}
- 从 words 集合中移除停用词
- 降低无意义词的 Jaccard 贡献

方案 B：引入 jieba 分词（生产环境）
- 对中文边界文本用 jieba 分词
- 中英文混合文本的 token 边界更准确
- 增加依赖

方案 C：按 2-gram 切分
- 将边界文本转为字符 bigram 集合
- "仅处理 HTTP" → {"仅处", "处理", "理H", "HT", "TP", "P ", " 4", "42", "29"}
- 天然处理中英文混合，无需额外依赖
```

### P2-16 校验结果只有 accept/reject，无合并建议

**问题**：`OverlapCheckResult` 只返回"是否允许创建"和"最大重叠率与哪个节点"，但不提供"应该合并到哪个节点"的建议。

**后果**：
- 子代理收到 `allows_creation=False` 后，需要自己判断合并策略
- 当前实现中，拒绝后什么都不做（举证包被丢弃）
- 没有机制告诉子代理"这个错误应该被归入现有节点 `network.http_429`"

**修复方向**：
```
方案 A：返回合并建议
- 在 OverlapCheckResult 中增加 merge_target 字段
- merge_target = max_overlap_with（重叠率最高的节点）
- 子代理收到拒绝时，自动将举证包关联到 merge_target

方案 B：增加置信度
- 如果 max_overlap > threshold 但 max_overlap_with 的重叠率不是压倒性优势
  （如 top 1 = 0.75, top 2 = 0.72），返回 LOW_CONFIDENCE 而非明确拒绝
- 低置信度时允许人工审核或创建独立节点

方案 C：增加动作建议枚举
- DECISION_ACCEPT：允许创建
- DECISION_MERGE：建议合并到 X
- DECISION_SPLIT：建议作为 X 的子节点分裂
- DECISION_UNCERTAIN：置信度不足，待人工审核
```

---

### P2-17 校验只触发于新建，不触发于更新

**问题**：重叠校验只在 `OfflinePlanner._phase_validate()` 中被调用，即仅在新建节点前检查。但已有节点的 stats 更新（如子代理 `distill()` 增加 freq）不会触发重叠校验。

**后果**：
- 两个高度重叠的节点可能因为"谁先创建谁"而永久并存
- 节点 A（先创建）和节点 B（后创建但被拒绝合并）→ 实际上 B 从未被创建，但如果校验在 A 创建前不存在，A 本身可能是冗余的
- 路由表膨胀的根源不是"新节点被错误地创建"，而是"已有节点之间没有二次校验"

**修复方向**：
```
方案 A：周期性路由表去重
- 子代理的 maintain() 周期中增加"重叠审计"步骤
- 对路由表所有节点做两两重叠检测
- 标记高度重叠的节点对，建议合并

方案 B：增量校验
- 子代理更新节点 stats 时，检查该节点与路由表其他节点的重叠
- 如果发现已有节点重叠度 > threshold，触发合并

方案 C：接受现状
- 重叠校验是"预防"机制，不是"修复"机制
- 已有节点的重叠靠人工定期清理
```

---

### P3-18 无历史记忆

**问题**：每次 `check()` 调用都是一次性的，没有记忆之前被拒绝过的举证包。如果同一个举证包被多次提交（如主代理多次遇到同一个未知错误），每次都会重新做全量扫描和拒绝。

**修复方向**：
```
方案 A：L1 缓存
- 缓存最近 N 次 check() 的结果（按 candidate_category_id + candidate_signature 做 key）
- 缓存有效期：5 分钟或路由表节点数变化时失效

方案 B：持久化拒绝记录
- 将被拒绝的举证包写入"拒绝日志"
- 子代理消费暂存时，跳过已在拒绝日志中且超过 N 次的举证包
- 避免同一错误反复被拒绝
```
